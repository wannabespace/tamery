# Colors & surfaces

## Three darkness levels

| Level | Tokens | Use |
|---|---|---|
| 1 canvas | `bg-body` | App background, tab-bar strip, sidebar backdrop (sidebar naked — no card) |
| 2 surface | `bg-background`, `bg-card` | Window pane, grouped lists, active tab |
| 3 elevated | `bg-input`, `bg-popover` | Buttons, inputs, chips, menus, active segmented pill |

- Level-2 and level-3 boxes take `rounded-xl` + the control hairline `ring ring-foreground/4`, never `border`: both are 0.5px in this repo, but a border lives inside the box and takes layout space while the ring sits outside it. Never `ring-[0.5px]`/`ring-1`. Panes take no shadow, grouped lists `shadow-xs`.
- **Every popup paints `bg-popover`** — popover, dropdown and context menu alike — and dark `--popover` sits between the pane and the fields (0.254 between 0.2437 and `--input`'s 0.2633): a step up so a popup over the table reads as its own surface, still below the fields so a field inside a popup stays raised.
- **A card inside a level-2 pane must be level 3** (`bg-popover`): `--card` and `--background` are the same value, so a `bg-card` block on a pane shows only its hairline and reads as unlayered.
- **The connection list is level 3** (`bg-popover`), as is its dashed add row's hover: it sits on the canvas in one column with the search field and toolbar buttons, and a level-2 card under level-3 controls reads as the sunken one.
- Glass floating chrome: `bg-popover/70` + `backdrop-blur` + `ring-foreground/4`.
- Table-page dock: no shared shell — a `pointer-events-none` row of self-surfaced controls, so the gaps click through.

## Shadows

Kit overrides `--shadow-*` (macOS diffuse). Use the scale; never inline `shadow-[...]` and never re-darken at a call site — a popup that reads flat is a token problem, fixed once in globals.css. The scale splits in two: **control tiers** (`2xs`…`sm`) stay near-invisible in both themes — they are the lip on a field, not a lift; **elevated tiers** (`md`…`2xl`) separate a floating panel from what is under it, and dark overrides them far heavier, because a shadow tuned for white is gone on a dark ground. Menu-like popups take `shadow-xl`. The hairline defines a popup's edge but carries no elevation on its own — the app stacks level-3 on level-3 (a `bg-popover` menu over a `bg-popover` card), where only the shadow says which one floats.

## Accent, muted, and the tint rule

Transactional emails use the sRGB equivalents of the app's primary accent (buttons, links) and light-theme `muted-foreground` (fine print such as attribution), since email clients cannot reliably render OKLCH. Fine print goes through `Base`'s `footnote`, under the footer links, never in the body.

- **Filled buttons hover opaque**: `default`, `destructive` and `secondary` hover to a `color-mix` of their fill with `--foreground`, never an alpha of the fill — an alpha hover lets whatever sits under the button show through, which on glass chrome (the grid's bottom dock) reads as a washed-out, disabled button. Mix a chromatic fill **`in oklab`**, never `in oklch`: the greys are written with hue 0, so an oklch mix rotates the fill's hue toward it — blue primary hovers purple.
- `--accent` is the **hover surface**: always `bg-accent`, never a per-call-site colour, never an alpha tint. The levels span only a few points of lightness, so one absolute value cannot sit the same distance from all three — globals.css therefore re-declares `--accent` per level surface in both themes, so every level hovers the same step (0.035 L) past itself and call sites stay unchanged. Dark also re-declares it on `bg-input`: dark fields are the lightest level, so a control hovering to its container's accent would barely change or go darker than its own fill. A tint on a solid surface reads as grime over a near-white card, changes strength with whatever is behind it, and lets content under a floating control show through it.
- **Every row and control hovers to `bg-accent`** — ghost and outline buttons, select and number-field triggers, kit `TableRow`, connection rows, navigator and recents rows. A table is not special enough for a quieter hover of its own. Where a list also carries a keyboard cursor, the highlight goes to `bg-foreground/10` so it still reads louder than hover; dense full-bleed lists (query logger) do the same, since light theme leaves almost nothing between `--background` and `--popover`.
- **Rows on the translucent canvas are the exception: they hover to `bg-foreground/5` and press or latch to `/10`.** Under vibrancy the canvas takes the wallpaper's tint and lightness, so a solid grey reads as a dead patch whose contrast drifts with the desktop, while a tint keeps a fixed step and picks up the tint like everything around it (native sidebars do the same). Only rows and ghost row-buttons (`variant="ghost-faint"`); controls on the canvas keep their solid level-3 fill and `bg-accent` hover.
- `--secondary` sits a clear step past every level's `--accent` in both themes, so a secondary chip (enum tags) stays visible on a hovered or highlighted row; retune it with `--accent`, never at the call site.
- A control inside a row that already hovers to `bg-accent` hovers and opens to a foreground tint (`bg-foreground/5`–`/10`), never `bg-accent`: the kit's `bg-accent` vanishes on the hovered row. Kit `Button` and `SelectTrigger` carry it as `variant="ghost-faint"` (`Button` also as `ghost-faint-muted` when it rests muted); `AppMenuButton` takes it through `render`. A ghost control on a tinted surface (banner, popover footer, a muted text button on the translucent canvas) is `variant="ghost-tint"`, or `ghost-tint-muted` when it rests muted, for the same reason.
- `--muted` = static darker backgrounds only (empty-state and avatar tiles, inline mono pills), **never** a hover state, and never code blocks — a fenced block reads on the pane it sits on, or on the field surface when it sits in a form ([patterns.md](patterns.md)). It is an asymmetric per-theme pair, so prefer it on level-2/3 surfaces. Skeleton fills use `bg-foreground/10`, because dark `--muted` sits too close to `--body` to show on the canvas. The segmented `Tabs` track is `bg-muted`, a well below every level in both themes: a `bg-foreground/N` track lightens in dark until it meets the `bg-input` pill.
- Latched icon toggle is `bg-foreground/10 text-foreground`, carried by the `ghost`/`outline` variants on `aria-pressed` — a toggle sets the attribute and never a className, and never adds `text-primary` on top (a blue glyph on a grey chip is two competing signals).
- **Kit components used as row links carry the foreground at the kit level**, not the call site: `Item` and the `ghost` `Button` set `[a]:text-foreground`, so a `render={<Link>}` keeps foreground text against the global `a { text-primary }` (Hard Rule 7) with no `text-foreground` repeated at every use. A variant that gains a link use adds the `[a]:` selector there.
- **A selected row is grey, never `bg-primary`**: `bg-foreground/15` under unchanged text and icons, the colour macOS lists draw selection in; a blue fill makes the active row the loudest thing in the window and forces every glyph on it to invert. It sits a step past the keyboard cursor's `/10` so selection and cursor stay apart; the cursor on the selected row deepens it to `/20`. **A list row never draws a focus ring**: keyboard focus on a row is the cursor fill (`focus-visible:bg-foreground/10`, `/20` on the selected row): a ring around a filled row doubles the focused search field's ring and reads as a second selection. Rings stay for standalone controls and cards. Zebra rows `bg-foreground/3` in the kit `Table`'s `sm` tier; the data grid draws hairline rules instead.
- **The hairline darkens with the hover fill**: any control carrying `ring ring-foreground/4` goes to `/12` on hover and while its popup is open — a control that lightens its fill but keeps a 4% edge reads as unlit. Static panes and popups keep `/4`; they are not hovered. **The checkbox is the exception and rides `/20` → `/35`**: it is the only control whose whole affordance is its hairline, so a 4% edge on a 16px white box disappears.

## Status surfaces (alerts, banners)

`destructive` / `success` share one recipe — `border-<token>/25 bg-<token>/10 text-<token>`, description at `/90`. The surface is the signal, so it has to read as tinted at a glance.

**An invalid field states its problem once**: the message carries `text-destructive` and the control carries the `aria-invalid` ring; the label stays `foreground`. Tinting the whole field cascades into every descendant without a colour of its own and makes one error shout three times.

## Cell highlights (data table)

Blue/neutral family, except drafts. Cursor, draft and error all paint one square overlay inside the cell, never the cell box itself. Strokes are `inset-ring` (outer rings bleed onto neighbours), never `ring-2`. The cursor is the input's focus ring drawn inset at 3px; it hides while the cell's editor card is open. A draft is a solid amber tint (`bg-warning/15`) under normal text — the unsaved-edit convention of native DB clients; blue reads as selection, a fainter tint vanishes on a hovered row, and coloured text reads wrong. No ring, no italic, no marker. An error pairs a faint fill with a stronger inset ring. A selected block is `bg-primary/10` on the same overlay, the cursor cell included under its ring, painted after the draft tint so a selection reads over drafts. A value a refetch changed flashes `bg-primary/20` fading out ([motion.md](motion.md)).

## Token definitions in globals

- Every colour token is a **literal `oklch()`** — never `var(--other-token)`; an alias inherits whatever the source token later gains, alpha included. The only permitted `var()` is `--surface-alpha`, only on `--body`. `.dark` carries only tokens whose values differ.
- **One translucency knob**: only `--body` carries the alpha (opaque on web, fullscreen and under the root `.opaque` class the Transparent background setting toggles; lower on mac). **The dark translucent canvas is capped, not just tinted**: vibrancy brightens with the wallpaper, so a tint near level 2's lightness lets the canvas reach the cards over a light desktop and every surface reads the same. There `--body` drops to a much darker tint at a higher alpha, sized so the composite stays a clear step below level 2 at the brightest the dark material gets; keep that inequality when retuning either value. **`--background` stays opaque**: it is reused as paint (tooltip text, avatar rings, toast fills), so alpha on it leaks everywhere. No per-call-site `bg-body/85` softeners: alphas multiply. Never reuse `--body` as text, ring or border, or behind `/N`; the one exception is `apps/main`, web-only so its alpha is always 1, whose shell mask has to be the canvas colour exactly.
- **Modals and fullscreen are opaque.** `backdrop-filter` cannot sample the OS vibrancy behind the page, so translucency rules opt out with `:not(:has([data-slot$='-overlay']))` on the root, affordable only while hot paths render no `data-slot` per row; **re-check if a virtualized list ever does** (fallback = a marker class). The fullscreen and setting gate is `:not(.window-fullscreen, .opaque)` on the same rules: a separate override block loses on specificity.

## Text selection

`::selection` is `bg-primary/30 text-primary`, flipping to white on a solid-primary surface. That selector must match the *slot*, not a class — surfaces are often painted by a parent's variant, leaving no class on the text's own element, so any new solid-primary surface needs adding there.

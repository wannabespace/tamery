# Product and domain terminology

## What Tamery is

AI-powered desktop/web app for managing database connections. Connection metadata + encrypted connection strings live locally (SQLite via OPFS); metadata optionally syncs to cloud.

## Terminology

Use precisely; avoid the listed synonyms.

- **Connection** — named, typed pointer to a database. Metadata only, never the raw string. _Avoid_: database, data source.
- **Connection String** — full URL including credentials. Always stored encrypted; never sent to cloud in plaintext. _Avoid_: credentials, DSN, URL.
  - **User, password and database are percent-encoded in the string.** Every writer encodes them (`connectionParts.format`, `resourceConnectionString` in `packages/connection/utils.ts` for a resource name) and every reader goes through `readConnectionString` (`packages/connection/parse-connection-string.ts`), which decodes tolerantly; SafeURL alone hands them back raw, so a driver fed from it sees `p%20w` instead of `p w`.
  - **Synced connection rows never carry the string**: the connections collection persists them as-is, so the sync and events endpoints omit it and a device gets each string only through `connections.resolve`, which it encrypts with the device key.
  - **The local proxy (`tamery proxy`) runs only the string the device sends**, never a lookup by id: the server's copy of a **No password** or **Metadata only** connection lacks what the device holds. The cloud proxy gets ids for a saved connection and refuses any host that resolves to a non-public address (loopback, private, link-local, shared, multicast, or one embedded in NAT64 or 6to4) and any string naming a certificate file (`sslca`, `sslcert`, `sslkey`, `sslrootcert`), which the drivers would read from its own disk (`apps/proxy/public-host.ts`).
  - **Transport encryption is never guessed down.** A Postgres or MySQL string without an SSL setting connects over TLS (unverified) and falls back to plaintext only when the server itself answers that it has no TLS, never after another error; an explicit off stays plaintext. A ClickHouse string is `https://` unless it says `http://` or the form names ClickHouse's plain port 8123. An Oracle listener speaks TLS only on its own TCPS port, so an Oracle string is plain TCP unless it says `ssl=true`; a MongoDB string is plain unless it says `tls=true` or is `mongodb+srv://`; nothing falls back either way.
  - **A SQLite connection is a file, Cloudflare D1 or a libSQL server, told apart by its string, never by a `ConnectionType`**: an empty host is a file (`sqlite://`) whatever the scheme says, and a server's scheme names its provider (`getProviderOfScheme`, `packages/connection/connection-parts.ts`, read into `ConnectionParts.provider`): `d1://` is Cloudflare D1 (host `api.cloudflare.com`, the account ID as user, the database ID as path), `libsql://` is Turso or any libSQL server. A scheme Tamery does not know is refused, never guessed to be a provider, so a new provider is a new scheme. A remote one keeps its token as the password, so stripping, restoring and syncing it follow every password; the form offers them as the providers **Turso** and **Cloudflare D1** but saves the type `sqlite`. **A SQLite file's string is `sqlite://` and the file's absolute path, never a host** (`packages/connection/sqlite-file.ts`). A `~/` path stays home-relative in the string and is expanded only where the file opens, so each computer reads it from its own home folder. The cloud proxy refuses an empty host and the executor opens a file only for one, so no server ever opens a file on its own disk; the desktop app and `tamery proxy` open it on the user's machine. Its one resource is `main` (`SQLITE_RESOURCE_NAME`), which `resourceConnectionString` leaves out of the string.
  - **A MongoDB string holds one host.** A pasted seed list keeps its first host (the driver finds a replica set's other members from it), and `mongodb+srv://` is the **MongoDB Atlas** provider, formatted without a port. MongoDB checks a login against the path's database unless `authSource` names another, so `resourceConnectionString` pins `authSource` to the string's database (`admin` when it names none) before it puts another resource in the path.
  - **Locally every string is encrypted with a device key**, not the workspace secret; how the key is kept is in `architecture.md` → Device key.
  - **SSH tunnel settings live inside the string** as `ssh_*` query params (`packages/connection/ssh/params.ts`), so encryption and sync carry them. `CloudWithoutSecrets` keeps secrets off the server through `connectionSecrets.strip` (`packages/connection/secrets.ts`), on the client before upload and on the server before encrypting. It **empties** each SSH secret, the SSL client key passphrase (`sslpassword`, `sslpassphrase`) and the inline PKCS#12 bundle (`sslpfx`) rather than dropping it (`sslkey`, `sslcert` and `sslrootcert` are file paths the drivers read, so they sync): an empty param is the marker for "this device must ask", which locks the connection behind its form, opened on just the missing fields, until they are filled, and `connectionSecrets.restore` refills only emptied params from the local copy, so a secret the synced string dropped never comes back; it refills the database password only while `isPasswordExists` is set, since an empty one otherwise means another device removed it. `isPasswordExists` still means the database password only. Option keys are case-insensitive to every driver, so every reader (and `connectionSecrets`) lowercases them through `readConnectionString`/`lowercaseKeys`; matching a raw key lets a pasted `sslPassword` slip past the strip. Oracle never offers one: node-oracledb opens its own socket and takes no stream, so its form has no tunnel field and its executor refuses `ssh_*` params. The MongoDB driver takes no stream either and dials every replica set member itself, so its executor serves the tunnel as a SOCKS5 proxy (`ssh/socks.ts`): loopback only, with random credentials per tunnel so no other local process can use it, and each connection the driver makes opens a channel to the host it names, resolved on the SSH host. Tunnels open **only in the desktop database process** (`architecture.md` → Desktop processes), which plugs `ssh/tunnel.ts` into the dialect clients through `ssh/forwarding.ts`; anywhere else (web, proxies, CLI `query`) a string carrying `ssh_*` params fails with `SSH_DESKTOP_ONLY`, so the clients never import ssh2 and the CLI bundle stays free of its native addon. The host key is checked against the user's and the system-wide known_hosts files, a host missing from all of them is trusted only through a native dialog that defaults to Cancel, which main shows for the database process, and a host listed under another key or key type is refused like a changed key. The driver talks to the database over a channel of the SSH session, so a tunnel opens no local port except MongoDB's SOCKS proxy. A host the SSH host can't resolve is looked up with `docker` there as a running container name or Compose service and forwarded to its bridge address (`ssh/docker.ts`), so a Compose stack's database needs no published port; a host that resolves, even to a refused port, is never redirected and runs no command there. Anything shown to the user is built from host, port and path, never the query string: the params can hold a private key. Copying a string (`connectionSecrets.copyable`) drops the SSH secrets and keeps the database password and SSL key passphrase, which another client needs to connect. `~/.ssh/config` fills what the form leaves empty, `Include`s followed; a host it sends through `ProxyJump` or `ProxyCommand` is refused rather than dialed directly. A host key the user trusts is also remembered for the run, so a read-only known_hosts never prompts again when a tunnel reopens.
- **Provider** — a service over a `ConnectionType` with its own fields and mark but the same dialect (`Provider`, `packages/shared/enums/connection-type.ts`): Turso and Cloudflare D1 over SQLite, MongoDB Atlas over MongoDB. The Engine select lists each type and then its providers. The connection row keeps it (`provider`) so the list, title bar and switcher show its mark without the string, also on a **Metadata only** device; the form saves the engine picked, and a paste or MCP's `create_connection` saves the one the string's scheme names (`ConnectionParts.provider`), so a new Turso domain needs no entry. It never decides how a query runs: the string's own host and scheme do. _Avoid_: vendor, service, host (in UI copy).
- **Workspace** — named group of connections. _Avoid_: organization (in UI copy), team, project.
- **Share** — a public, read-only link (`share.tamery.app/<id>`) to one table's rows: the columns the table shows in its order, optionally its filters, in the table's sort. A table holds any number, one per view: the dialog opens on the share whose stored view matches what the table shows (columns, filters, sort) and starts a new link when none does, and saving an older share stores the current view in it, keeping its id. _Avoid_: publish, embed, public table.
  - **Only a connection synced with Full can be shared**: viewers have no device, so the server must hold the whole string. Sync type is fixed at creation, so a share only goes away with its connection (cascade) or by **Stop sharing**.
  - **The proxy runs every share query, never the API**, and builds it itself from the stored view (`apps/proxy/share-rows.ts`) with the app's own spelling and filter bindings: the client never sends SQL, a filter's operator must be one `SQL_OPERATORS` knows (it reaches SQL through `sql.raw`). Viewers cannot reorder the rows — the link is read-only — and the order reported for the header indicators names only shown columns. The host goes through the cloud proxy's public-host and server-file checks every time; saving first runs the same query through `shares.check`, so a local, private or unreachable database is refused before a link exists.
  - **Pages are cached in the proxy for the share's refresh interval**, keyed by the share's `updatedAt`, so a save shows at once; **Live** still caches a few seconds. The cache is a bounded LRU, each share exposes at most its own `maxRows` (a plain column the owner sets in the dialog, up to `SHARE_MAX_ROWS` = `SHARE_PAGE_SIZE × SHARE_MAX_PAGES`), and each share's cache misses are rate limited, so a public link can neither grow the proxy's memory nor hammer the owner's database. Only the first page flips `failingSince` through `internal.shares.report`, which the owner's list on the share site shows, so no viewer's deeper page can mark a share failing.
  - The view (the shown columns with the kind the app drew them by, every column's type for filter binding, filters, order) is stored encrypted, so the share page draws the same glyph and checkbox as the app without classifying types again; the password only as a Bun argon2 hash. Shares are online-only: a plain oRPC list, not a collection, since saving needs the server's reachability check anyway. The free plan holds `FREE_SHARE_LIMIT` unexpired shares at once (`share.create`), counted and saved under a lock on the user's row so concurrent saves cannot pass it.
- **Tab** — every view inside a connection resource: `table`, `runner`, `definitions`, `visualizer`. _Avoid_: page, view, screen.
- **Navigator** — the only sidebar.
- **Agent mode** — a per-device switch (title bar, ⇧⌘L) that turns the open connection into its chat: the Navigator lists the resource's chats, the tab strip holds the open chats, the workspace is the active chat. It changes the chrome only; tabs, the side chat panel's open state and the URL are left as they were and come back when it is off. _Avoid_: chat mode, AI mode.
- **Schema note** — a fact the user keeps about a database that its schema does not say ("amounts are in cents", "status 3 = refunded"), on the whole resource, a table or a column. A synced collection (`schemaNotesCollection`, the `schema_notes` table, its text encrypted at rest) owned like saved queries; every AI prompt about the resource gets them — the chat's instructions on the server, the filter, completion, fix and update contexts on the client (`schemaNotes.inContext`) — and `describe_table` returns a table's own. The chat agent proposes one through `propose_note`, which, like `execute`, never answers itself: nothing is saved until the user presses Save on its card. Edited by hand in the visualizer's inspector. _Avoid_: annotation, memory, semantic layer (in UI copy).
- **SyncType** — credential handling during cloud sync: `Cloud`, `CloudWithoutSecrets`, `CloudWithoutConnectionString`, shown as **Full**, **No password** and **Metadata only**. The last stores a null connection string server-side, so its row never reaches another device's `connectionStringsCollection`; there an absent row is final, not "resolving", and the connection opens its form for the user to enter the server details, which stay on that device. _Avoid_: sync mode, cloud mode.
- **Collections** — client data in TanStack DB collections, persisted to SQLite; synced ones stream from cloud via oRPC event iterators.

**On MongoDB the UI says collection, field and document** where it says table, column and row on SQL: copy takes the noun from `getCapabilities(dialect).names` (`useObjectNames()` under a resource), never a literal "table", "column" or "row", so a new engine with its own words is one capability entry. Code and ids keep table, column and row.

User-facing names differ from internal ids in two places: **Query** is the user-facing name for a `runner`, and **Schema** for `definitions` (the umbrella has to cover the visualizer too).

## Collections

- A catch-up request sends only `{ id, updatedAt }` per row — whole rows would re-upload every payload on each reconnect. **An empty array is a normal request, not a failure**: the server answers with everything.
- **Writes to synced collections go through `mutateOffline`** (`core/collections.ts`, TanStack `offline-transactions`): the write applies at once, waits in the IndexedDB outbox, and replays FIFO when online. Synced collections have no `onInsert`/`onUpdate`/`onDelete`, so a bare `insert` outside it throws. Each collection's `mutations` sends one row and lists only the operations the app issues — a missing one rolls back instead of retrying, since a retried write blocks the FIFO outbox. The executor retries every other error except a non-5xx `ORPCError`, which rolls back. Retries mean server `create` and `remove` **must be idempotent** (`onConflictDoNothing`, a plan-limit count that excludes the incoming id, a remove that succeeds on a missing row), or a lost response turns into a duplicate-key 500 retried forever or a `FORBIDDEN`/`NOT_FOUND` rollback.
- **The catch-up sends the server versions** (the collection's synced layer), never visible rows: an unsent insert is unknown to the server, whose answer would delete it, and a row with a pending edit or delete must still report the version the server holds, or the answer resurrects it or overwrites the replay. A `create` whose unique key already holds another row returns that row, and `push` writes it in place of the client's.
- Only the Web Locks leader window persists the outbox; other windows of the same app write online-only (the library's fallback).
- Online-only by nature: auth, workspace creation (subscription-gated server-side), AI.
- `connectionStringsCollection` is local-only, rebuilt by round-trip: **an absent row means "not resolved yet", never a negative answer** — a missing row maps to the `resolving-password` flow (blocked, no password prompt).
- `getCollections()` lazily creates the singleton set; `_protected`'s `beforeLoad` awaits readiness and puts it in route context. **That await is first-render latency, so a collection joins it only if something reads it synchronously** — the ones backing `$resourceId` redirects and the prefetch do; the chat's three are reached only through live queries and stay out.
- **Only `fullSignOut` may call `cleanCollections()`.** Components read collections from route context, everything else from `getCollections()` — dropping the singleton while a `_protected` match is alive splits the two: the router keeps the old set in cached context while the next `getCollections()` mints an empty one, and every query throws.

## Workspaces

Better Auth's `organization` plugin is remapped to `workspace`; the plugin's `activeOrganizationId` field points at the `activeWorkspaceId` column.

- Every user gets a lazily-created **default personal workspace**; `connections.create` falls back to it.
- Extra workspaces are gated by `workspace.create`. Deletion is **disabled** — connections cascade and there is no delete flow yet.
- The client scopes connections to the active workspace **inside** each `useLiveQuery`, never a post-query `.filter()` (a new array every render).
- Workspaces reach the client through `workspacesCollection`, **not** Better Auth's `useListOrganizations` — the list must survive offline.
- Active workspace is per-device `localStorage`, **never** pushed to the session; callers pass the active id explicitly to Better Auth endpoints.
- `connections.create` accepts the client's `workspaceId` (membership-checked) so offline-created connections land in the device-active workspace. Multi-member and invites are not built yet.

## Early access

**Temporary**: the whole gate goes away when early access ends, so nothing else builds on it (no new reads of `early_access`, no UI that assumes it). Removing it is `git revert` of PR #546's merge commit, which restores the previous copy and guest sign-in word for word; keep that PR's migration folder (applied in production, and its snapshot is what lets `drizzle-kit generate` produce the `DROP TABLE`) and generate a new migration. Only emails approved in the `early_access` table (`granted_at` set) can use Tamery, existing accounts included. `apps/api/lib/early-access.ts` checks before a sign-in code is sent, before a user is created and before every session is created; a refused email is added to the table and the client lands on the site's `/early-access` page (`EARLY_ACCESS_ERROR_CODE`, social sign-ins through `errorCallbackURL` → `/sign-in?error=`). Approving is `bun scripts/grant-early-access.ts <email…>` in `apps/api`, run inside the API's Railway container (`railway ssh`) so it gets production env: it sets `granted_at` and emails the person that their account is ready. A session already open is not checked again, so revoking an email also means deleting its sessions. Guest sign-in is refused while early access lasts and the desktop app offers no **Continue without an account**.

## Anonymous users

Desktop-only "Continue without an account" signs in through Better Auth's `anonymous` plugin, so an anonymous user is a real server user with a default workspace and its own encryption key — every sync and encryption path stays shared.

- **Getting in stays easy.** Anything that helps someone get their first connection working (the form, parsing, test, diagnosis, Explain with AI on a failed test) is free for guests and Free users, with no quota or sign-in gate; limits only gate what comes after.
- Limits are the `guest` plan in `packages/shared/permissions.ts`: one connection (`connection.create` with the current count), no AI (`ai.*`) beyond connection diagnosis, no workspaces, one open tab per resource (`tab.multiple`, client-only: `openTab`/`ensureTab` close the other tabs first, so opening another replaces it silently). Guests can edit the database like any member. A locked control's press goes through `checkOrUpgrade` (`architecture.md` → Permissions), which for a guest is the banner prompt `promptSignIn` — it also sends the PostHog event `guest_feature_blocked { hint }`, the signal for which limits push guests to sign up. How a locked control looks is `tamery-ui` patterns. The server checks are the real gate; `handleError` shows a guest's `FORBIDDEN` message in the banner (toasts on `/auth`, which has no banner).
- Upgrading goes through the desktop challenge `exchange`, which still carries the anonymous bearer: it moves the anonymous user's connections (same ids; a guest's have no stored string, so nothing is re-encrypted) and queries into the real user's default workspace, then deletes the anonymous user. A failed move fails the exchange — the transaction rolls back and the guest session stays valid, so signing in again retries it. Better Auth's own `onLinkAccount` never fires here — the real sign-in happens in the browser, not in the anonymous session. The client reloads afterwards so sync streams reopen as the new user.

## Tabs

Tabs live in `connectionResourceStore.tabs` as `{ id, preview?, title? }`, persisted per resource in `localStorage`; import that store from `~/core/connection/stores`. The type lives in the id alone: each tab module registers a kind that matches its ids.

- A tab id is readable, self-describing, and the single route path param; `resolveTab` turns one back into a kind and params, so deep links work; an id no registered kind matches is closed. Runner is the **only** multi-instance type.
- `$tabId`'s `beforeLoad` must stay **pure** — it runs on hover preload and must not touch the store; a component effect calls `ensureTab` + `setActiveTab`.
- The resource index redirects to the active tab while it is still listed, so code that leaves a tab whose object is gone (a dropped table, a dropped or renamed schema) **removes the tab before navigating** to the index — the other order lands back on the stale tab.
- `tabLabels` derives the whole strip at once, since qualification and numbering depend on the other open tabs.
- Activating a table tab records it in the table module's recent list; the empty pane lists the ones still present in the catalog.
- Table tabs carry `preview`: single click is a preview (italic, reused), double click promotes it. A tab may also carry an optional user `title`, cleared when emptied or equal to the derived label.

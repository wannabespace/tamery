# oRPC routers, secrets, and environment

## oRPC

- Copy the shape from a neighbouring router in `apps/api/orpc/routers/` and register it in `routers/index.ts`. `authMiddleware` puts `user`/`session` on context; `accountMiddleware` does the same and rejects guests (`FORBIDDEN`); `permissionsMiddleware` adds `context.permissions` (`architecture.md` → Permissions). Clients call through the generated `ORPCRouter` type, never a manual fetch.
- `apps/api` is a composite project whose emitted `.types` are what clients type-check against: after changing a router, run `tsc` in `apps/api` before `check-types` elsewhere, or clients check against the old contract.
- `create` and `remove` procedures take exactly one item — never `type.or(schema, schema.array())`; the offline outbox sends one row per call.
- **No `.output()` schemas** — the handler's inferred return type already is the client contract; an output schema only duplicates it and re-validates the server's own data on every call. The exception is a schema that also types something else — the sync collections' Redis publisher, `banner`'s accumulated items.
- **Errors are declared, not constructed**: a procedure or middleware lists its codes in `.errors({ CODE: { message } })` and throws `errors.CODE()`, so the code and its message live in the contract the client is generated from. `new ORPCError(...)` only where no `errors` map exists — handler interceptors and helpers outside a procedure. Clients narrow with `isDefinedError`.
- **`internal.*` is the proxy's API**, gated by `proxySecretMiddleware` (`x-proxy-token`). `internal.shares.resolve` is the one path that hands out a decrypted connection string without a user session, so it refuses an expired share or one whose connection is no longer synced with Full, and checks the password before decrypting. Every password attempt is rate limited in Redis (`@orpc/ratelimit`) per share and viewer network (the proxy's `x-real-ip` through better-auth's `normalizeIP`, so an IPv6 viewer counts by its /64) with a far higher share-wide cap behind it, and is counted before verifying: counting only failures after a slow argon2 verify lets parallel guesses all pass. Keying by viewer keeps a stranger's guesses from locking everyone else out; the share-wide cap keeps a guesser with many addresses bounded. A right password answers with an unlock token (an HMAC over the share id and its password hash), which the share site keeps in an httpOnly cookie and sends instead of the password, so a page load never runs argon2 and changing the password turns every earlier viewer away.
- **An error passed through the proxy keeps its type only if the proxy declares it too.** oRPC marks a rethrown error as defined only when the procedure's own `.errors()` lists its code, so the API's `internal.shares.resolve` and the proxy's `shares.*` spread the same maps from `@tamery/shared/share`, and the share site reads them with `safe()`'s `definedError` instead of matching code strings.
- `syncDiff`'s `updated` query is optional: an insert-only collection omits it rather than paying an `OR` branch per client row for a match that cannot happen.

## Chat

- Stack: AI SDK (`ai` v7 + `@ai-sdk/react`) + OpenRouter (`@openrouter/ai-sdk-provider`, the only model provider package) + `ai-retry` (cross-model fallbacks) + `ai-resumable-stream` (Redis). Not `@tanstack/ai`.
- `ai.stream`: the wire carries only the new turn; the stored transcript is the model context, so a client can never send stale history. Titles generate server-side beside the first answer.
- `ai.attachStream` answers "what should be streaming into this chat right now" — the live stream when one exists (a pointer per chat, not per device), else a fresh stream when the transcript ends on a user turn that never concluded, decided once on the server. A turn that ended carries its own evidence (answered and failed turns persist an assistant message, a stopped one flags the user message), so only a crash mid-stream is eligible for the restart. Empty is nothing to stream, never an error. Deliberately not named `resume` — it can spend a model call.
- `ai.abortStream` publishes stop through Redis and flags the user turn stopped before it returns, so no tab re-attaches to a turn the user stopped; a client that merely leaves stops nothing.
- No output schemas on streaming procedures (the chunk union belongs to `ai`), and `ai.stream`'s `messages` schema stays loose — `validateUIMessages` is the real check and the loose shape keeps old clients valid.
- **Never wire the request signal into `streamText`** — streams are detached on purpose; only `chatStream.stop` aborts. A reload is not a cancellation.
- **One starter**: `chatStream.claim` sets the Redis pointer with **NX** and returns `null` to the loser, so both senders fall back to resuming the winner's stream and two tabs racing one turn watch one answer. `CONFLICT` is only for a pointer whose stream is already gone. The pointer is released on flush or a failed resume, and expires after an hour.
- **Ids are the idempotency**: the user turn's uuid v7 is minted client-side and is the row id (a re-ask lands on `onConflictDoNothing`); assistant ids are minted server-side. A re-ask therefore leaves the transcript ending on an assistant turn — that is what a regenerate looks like on the wire, so `ai.stream` deletes that answer before building the model context instead of asking the model to continue it. The UI stream's `onEnd` persists the assistant row, and the stream only ends once `onEnd` settles, so the resumable Redis stream stays open until the row lands: a reload mid-finish rejoins or finds the row, never neither. Keep the persist inside `onEnd` (awaited), not in a detached callback.
- **`@tamery/ai` vs `apps/api` splits by dependency, not topic**: db/auth/oRPC stays in the app; models and stream lifecycle live in the package; persistence is handed in as `onFinish`. Provider fallbacks live only in the package's model list.
- **Usage**: capture is the package's, the row is the app's. `createAiUsage(onRecord)` hands persistence in the way `chatStream` takes `onFinish`, and returns `telemetry(scope)`, a per-call AI SDK telemetry integration, **not** a global registration and no ambient context. Pass it as the `telemetry` option of any model call and that call reports itself, with the `modelId` that actually answered, so an `ai-retry` fallback is reported as itself; a closure beats async context for a detached stream, and a call passing no telemetry records nothing (which is what keeps frozen chat v1 out). A call made outside the AI SDK (Codestral's fill-in-the-middle fetch) reports through the returned `record(scope, modelId, usage)`. **Structured output goes through `generateText` with `Output.object`, never `generateObject`**: it is deprecated in this SDK and skips the model-level hook, so nothing would be recorded. **Aborted streams record nothing and cannot**: the provider never sends a finish chunk, so no token counts exist. **An output schema has no optional keys**: `@tamery/shared/arktype-config` turns `exactOptionalPropertyTypes` off, so `'key?'` becomes `T | undefined`, which has no JSON Schema form and fails every call at runtime (`ToJsonSchemaError`); make the key required and `| null`.
- Errors surface generic; provider errors stay in server logs. Per-instance ownership is the upgrade path for a second api instance.
- **Client**: one `Chat` instance memoized outside React per chat id — identity never changes under a running send. `useChat` holds only the live exchange; settled turns come from the collections, merged by id, persisted rows winning. So a chat reopened from the collections has no live turns and `regenerate()` would throw — Retry re-sends the last user message under its persisted id, which the server reads as a re-ask. The SDK's mount-only `resume` option is not used: every tab attaches whenever the merged transcript ends on a user turn and the instance is idle, so a turn started in one tab streams into all of them. Re-entry is self-limiting. The transport maps an empty `attachStream` body to `null`, the SDK's "no active stream" signal — an empty stream would instead run the full request lifecycle (submitted flash, phantom finish).

## Secrets / environment

- **Logs go through `sanitizeLogData`** (`@tamery/shared/sanitize-log`), and a driver's `error` event through `logDriverError`, never a bare `console.error`: pg-pool hands its listener the client, which Bun prints with its non-enumerable `password`.
- Each app's `env.ts` validates env vars with ArkType. In development, service URLs default dynamically via portless (`monorepo.md`) — don't add them back to `.env`.
- **In production the two wrapping keys are not raw env.** `USER_KEY_SECRET`/`ENCRYPTION_SECRET` are stored KMS-wrapped (`*_WRAPPED`) and unwrapped by `apps/api/lib/unwrap-secrets.ts` (through `lib/kms.ts`, Infisical KMS) into `process.env` **before** `./env` and `@tamery/db` read them — so a leaked env buys only the wrapped blobs plus a revocable Infisical machine-identity credential, never the keys. It runs as a Bun `--preload` in `start` and the `rotate:*` scripts, **never as an import**: Bun evaluates later sibling imports while an earlier one's top-level await is still pending, so an `import './lib/unwrap-secrets'` above `./env` does not hold it back. Dev/test keep plaintext `*_SECRET` in `.env` and the unwrap short-circuits when the plaintext is already present, so Infisical is never contacted locally. Re-wrapping (new KMS key, same plaintext) leaves stored data untouched. `apps/api/scripts/wrap-secret.ts` wraps a plaintext secret (stdin → ciphertext). Operator steps (setup, rotation, recovery): `apps/api/SECRETS.md`.
- **Rotating a wrapping key's value is a keyring** (`packages/db/utils.ts`): `ENCRYPTION_SECRET`/`USER_KEY_SECRET` may hold a comma-separated list, current key first (so a key itself never contains a comma) — new rows encrypt under the current key, every key is tried on decrypt (AES-GCM's tag rejects the wrong ones). Rotation goes straight to `new,old`, accepting that during the deploy overlap an instance still on the old keyring fails to read the few rows a new instance just wrote; a retired key's offline copy outlives every database backup holding rows under it. Steps: `apps/api/SECRETS.md` → Rotation. The ciphertext format is unchanged, so rows written before the keyring need no migration. This rotates the key itself; re-wrapping above only changes the KMS custody of one key.
- **Run the rotate scripts through `bun run rotate:*`** in `apps/api` (the unwrap preload), inside the API service against its wrapped env, so no plaintext secret passes through a shell; dry-run by default, `--execute` applies. `encryption-secret.ts`/`user-key-secret.ts` re-encrypt every column a wrapping key protects under its current key with no wrapping transaction — under the keyring a half-done run is a valid state, so an interrupted run is just repeated. `connection-keys.ts` rotates a user's (or all users') per-user key — the inner connection-string layer — with no env change or redeploy, minting a fresh key and re-encrypting that user's key row and connections together per transaction.
- Each user's connection-string key is a random secret in `user_encryption_keys`, wrapped at rest by `USER_KEY_SECRET` via `encryptedTextColumn(env.USER_KEY_SECRET)`. `userEncryptionKey.create(userId)` mints it in `databaseHooks.user.create.after` (rolling the user back if it fails); `userEncryptionKey.get(userId)` reads it (`apps/api/lib/encryption-key.ts`). A user delete cascades the row (crypto-shred), so no delete hook.
- Connection strings are encrypted per **workspace**, not per requester: `getWorkspaceSecret(workspaceId)` resolves the workspace owner's key and every decrypt path passes the row's own `workspaceId`, so shared workspaces decrypt with one key once invites ship.

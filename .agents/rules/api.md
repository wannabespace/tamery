# oRPC routers, secrets, and environment

## oRPC

- Copy the shape from a neighbouring router in `apps/api/orpc/routers/` and register it in `routers/index.ts`. `authMiddleware` puts `user`/`session` on context; `accountMiddleware` does the same and rejects guests (`FORBIDDEN`); `permissionsMiddleware` adds `context.permissions` (`architecture.md` → Permissions). Clients call through the generated `ORPCRouter` type, never a manual fetch.
- `apps/api` is a composite project whose emitted `.types` are what clients type-check against: after changing a router, run `tsc` in `apps/api` before `check-types` elsewhere, or clients check against the old contract.
- `create` and `remove` procedures take exactly one item — never `type.or(schema, schema.array())`; the offline outbox sends one row per call.
- **No `.output()` schemas** — the handler's inferred return type already is the client contract; an output schema only duplicates it and re-validates the server's own data on every call. The exception is a schema that also types something else — the sync collections' Redis publisher, `banner`'s accumulated items.
- **Errors are declared, not constructed**: a procedure or middleware lists its codes in `.errors({ CODE: { message } })` and throws `errors.CODE()`, so the code and its message live in the contract the client is generated from. `new ORPCError(...)` only where no `errors` map exists — handler interceptors and helpers outside a procedure. Clients narrow with `isDefinedError`.
- **`internal.*` is the proxy's API**, gated by `proxySecretMiddleware` (`x-proxy-token`). `internal.shares.resolve` is the one path that hands out a decrypted connection string without a user session, so it refuses an expired share or one whose connection is no longer synced with Full, and checks the password before decrypting. Every password attempt is rate limited in Redis (`@orpc/ratelimit`) per share and viewer network (the proxy's `cf-connecting-ip` through better-auth's `normalizeIP`, so an IPv6 viewer counts by its /64) with a far higher share-wide cap behind it, and is counted before verifying: counting only failures after a slow argon2 verify lets parallel guesses all pass. Keying by viewer keeps a stranger's guesses from locking everyone else out; the share-wide cap keeps a guesser with many addresses bounded. A right password answers with an unlock token (an HMAC over the share id and its password hash), which the share site keeps in an httpOnly cookie and sends instead of the password, so a page load never runs argon2 and changing the password turns every earlier viewer away.
- **A proxied query checks its session once.** `internal.proxy.resolveConnectionString` runs `authMiddleware` and, when the proxy sends `withUserId`, answers with the session's `userId` beside the string, and the proxy takes that as the query's owner, so a query by connection or resource costs that one API call and no `/auth/get-session` of its own. Only a raw connection string and a transaction step, which never reach the API, check the session through `/auth/get-session`. No session cache in the proxy: it would keep a revoked session working until the entry expired. The API and the proxy deploy in parallel and roll back one at a time, so the API still answers a caller that does not ask with the bare string, and the proxy falls back to `/auth/get-session` when an API without `withUserId` does the same.
- **A sign-in challenge (`account.challenge.*`) is handed a session only for a device that asked for it.** Whoever holds the verifier gets the session, so anyone can mail a victim a confirm link for their own challenge: the desktop app and the CLI open the browser only after their own `listen` registered the challenge with its IP and User-Agent, and `publish` refuses one nobody registered. The attacker's own device registers too, so against a mailed link only the confirm page's warning and the new-sign-in email stand: the page shows no device or code to compare. `newUser` is decided on the server from the account's age, since a client-sent flag would also switch off the new-sign-in email. The web app signs in with the site's cookie and never exchanges, so `type=web` only lands on `/open`.
- **The new-sign-in email goes only to a device the account has not signed in from.** A device is the versionless browser + OS and the IP's city, kept per user in Redis for 180 days and recorded at sign-up too; so an attacker on the same browser, OS and city as the victim gets no email. A Redis failure counts as a new device.
- **An error passed through the proxy keeps its type only if the proxy declares it too.** oRPC marks a rethrown error as defined only when the procedure's own `.errors()` lists its code, so the API's `internal.shares.resolve` and the proxy's `shares.*` spread the same maps from `@tamery/shared/share`, and the share site reads them with `safe()`'s `definedError` instead of matching code strings.
- `syncDiff` diffs in memory: a router gives it `versions` (the id and `updatedAt` of every row the user may see, a light indexed read) and `rows` (full rows for the ids that changed), never a query per client row or a parameter per id. A client sends every id it holds on each reconnect, so ids go to Postgres as one array through `idIn`: `inArray` binds one parameter per id and Postgres refuses past 65535.
- **Work that outlives its response goes through `runInBackground`** (`@tamery/shared/background`), since SIGTERM waits for it up to `DRAIN_LIMIT_MS` (`apps/api/lib/shutdown.ts`). Cloud Run kills the instance 10 seconds after SIGTERM, so the limit stays under that. Sync publishes stay unawaited and untracked: Redis queues commands while offline, so awaiting one would hang the write through an outage, and closing the client at shutdown sends what is queued.
- **A Stripe call made while a transaction holds a lock is bounded**: it passes `STRIPE_UNDER_LOCK` (`apps/api/lib/stripe.ts`, 15 s and one retry), the transaction runs `LOCK_TIMEOUT` (5 s) before taking the lock, and an error `timedOutUnderLock` recognizes answers a retryable error. With the client's defaults (80 s, 2 retries per call) a slow Stripe would hold the lock and a pool connection for minutes, and every waiter with it.

## Chat

- Stack: AI SDK (`ai` v7 + `@ai-sdk/react`) + OpenRouter (`@openrouter/ai-sdk-provider`, the only provider Tamery's own account calls) + `ai-retry` (cross-model fallbacks) + `ai-resumable-stream` (Redis). Not `@tanstack/ai`. `@ai-sdk/anthropic`, `@ai-sdk/openai` and `@ai-sdk/google` serve users' own keys only, an own OpenRouter key reuses `openRouterModels` (see Own keys), pinned to the `@ai-sdk/provider-utils` that `ai` resolves, since a second copy splits the tool types.
- `ai.stream`: the wire carries only the new turn; the stored transcript is the model context, so a client can never send stale history. Titles generate server-side beside the first answer.
- `ai.attachStream` answers "what should be streaming into this chat right now" — the live stream when one exists (a pointer per chat, not per device), else a fresh stream when the transcript ends on a user turn that never concluded, decided once on the server. A turn that ended carries its own evidence (answered and failed turns persist an assistant message, a stopped one flags the user message), so only a crash mid-stream is eligible for the restart. Empty is nothing to stream, never an error. Deliberately not named `resume` — it can spend a model call.
- `ai.abortStream` publishes stop through Redis and flags the user turn stopped before it returns, so no tab re-attaches to a turn the user stopped; a client that merely leaves stops nothing.
- No output schemas on streaming procedures (the chunk union belongs to `ai`), and `ai.stream`'s `messages` schema stays loose — `validateUIMessages` is the real check and the loose shape keeps old clients valid.
- **Never wire the request signal into `streamText`** — streams are detached on purpose; only `chatStream.stop` aborts. A reload is not a cancellation.
- **One starter**: `chatStream.claim` sets the Redis pointer with **NX** and returns `null` to the loser, so both senders fall back to resuming the winner's stream and two tabs racing one turn watch one answer. `CONFLICT` is only for a pointer whose stream is already gone. The pointer is released on flush or a failed resume, and expires after an hour.
- **One window answers each tool call**: every window attached to a turn gets its tool calls, so before reading, running, skipping or answering one it claims it through `ai.claimToolCall` (`chatStream.claimToolCall`, Redis **NX** keyed by chat and call, holding the window's id so the same window can claim again). The loser only watches the winner's output arrive, and a pending change it lost shows **Decided in another window**. A claim the API cannot answer lets the window go on alone, as a single window would.
- **Ids are the idempotency**: the user turn's uuid v7 is minted client-side and is the row id; assistant ids are minted server-side. A user turn whose id is already stored is a regenerate or an edit (the client resends the message under its own id), so `ai.stream` first drops it and every later message (`truncateFrom`, which also clears a compaction that covered them) and stores it again: the model never continues a stale answer, and both actions share one wire shape.
- **Compaction**: a chat's `compaction` (encrypted, synced, never writable through `chats.update`) is a summary standing in for every message through `throughMessageId`; `ai.stream`/`ai.attachStream` send the model only what follows it, with the summary in the instructions. A new user turn compacts first when the rest would fill `COMPACT_AT` of the resolved window, and `ai.compact` does it on demand; both summarize only what precedes the last user message, so a turn in progress keeps its own messages and its tool steps never lose their context. The summary runs on `models.summary` (a 1M-window model, since it reads up to a full window) and is recorded as chat usage. `fitContext` stays as the backstop for a single turn larger than the window.
- **Answer metadata** carries `model`, `startedAt`/`finishedAt` (across the turn's steps) and `context`, the last step's input tokens: the composer's context ring reads it, and `ai.chatCost` sums `ai_usage.cost` of the chat and its subagents for the rest. The UI stream's `onEnd` persists the assistant row, and the stream only ends once `onEnd` settles, so the resumable Redis stream stays open until the row lands: a reload mid-finish rejoins or finds the row, never neither. Keep the persist inside `onEnd` (awaited), not in a detached callback.
- **`@tamery/ai` vs `apps/api` splits by dependency, not topic**: db/auth/oRPC stays in the app; models and stream lifecycle live in the package; persistence is handed in as `onFinish`. Provider fallbacks live only in the package's model list, and the chat uses them only on Auto (`ChatPick.auto`): a model the user picked answers or fails, so a chat never moves their data to a company they did not choose. The chat's models are the curated `chatModels` there: `ai.models` serves them to the picker, and `ai.stream`/`ai.attachStream` take the pick as an id; no pick, or one no longer listed, is **Auto** (`pickChatModel`): Jev (`askJev`, a `score` question, one level per model) rates each new user turn into a level of `AUTO_CHAT_MODELS` and `AUTO_CHAT_EFFORTS`, Sonnet at medium when it cannot answer, the answer's metadata records its `model` and `effort` so the turn's tool steps stay on them, and a chat never steps down a model tier, since a lighter model re-reads the history without the cache; the effort follows each turn's own level. Plus per-model options: an OpenRouter `reasoning.effort` from `CHAT_EFFORTS`, a context window resolved by `resolveChatContext` (the model's full window or `STANDARD_CHAT_CONTEXT`; `streamChatStep` drops the oldest turns to fit it, on the model context only — the stored transcript stays whole) and `fast`, which routes through OpenRouter's `:nitro` shortcut. Every listed model must take tools and `reasoning` on OpenRouter.
- **Usage**: capture is the package's, the row is the app's. `createAiUsage(onRecord)` hands persistence in the way `chatStream` takes `onFinish`, and returns `telemetry(scope)`, a per-call AI SDK telemetry integration, **not** a global registration and no ambient context. Pass it as the `telemetry` option of any model call and that call reports itself, with the `modelId` that actually answered, so an `ai-retry` fallback is reported as itself; a closure beats async context for a detached stream, and a call passing no telemetry records nothing (which is what keeps frozen chat v1 out). A call made outside the AI SDK (Codestral's fill-in-the-middle fetch) reports through the returned `record(scope, modelId, usage)`. **Structured output goes through `generateText` with `Output.object`, never `generateObject`**: it is deprecated in this SDK and skips the model-level hook, so nothing would be recorded. **Aborted streams record nothing and cannot**: the provider never sends a finish chunk, so no token counts exist. **An output schema has no optional keys**: `@tamery/shared/arktype-config` turns `exactOptionalPropertyTypes` off, so `'key?'` becomes `T | undefined`, which has no JSON Schema form and fails every call at runtime (`ToJsonSchemaError`); make the key required and `| null`.
- **Cost**: a call through OpenRouter is recorded at the cost OpenRouter reports, plus the provider's own bill (`costDetails.upstreamInferenceCost`) when the provider runs on Tamery's own key (BYOK), where OpenRouter's `cost` is only its fee and often 0; a call OpenRouter reports no cost or a total of 0 for, or any other call, is priced by `getModelCost` from LiteLLM's table, trying the id, its bare name with dots as dashes and the provider without dashes (`xai/…`); a call that spent tokens and still has no cost is stored with no cost, so it spends no credits, and `apps/api/lib/ai-usage.ts` logs it and emails an Alert to `ALERTS_EMAIL`, so a model priced elsewhere (Codestral, under `mistral/`) is recorded with that prefix. `packages/ai/economics.ts` estimates a Free, Pro and trial month from the real prompts, `AI_QUERY_LIMITS`, `MODEL_IDS`, `FREE_WEEKLY_LIMITS`, `CHAT_LIMITS` and `PRO_PRICE_USD`; any change to a model, a prompt, an input cap, a limit or a price runs `bun run economics` in `packages/ai` before and after and reports the cost per call and Pro's margin, and `economics.test.ts` holds the budget, never raised without saying what it costs.
- **Own keys (BYOK)**: a user may save an Anthropic, OpenAI, Google and OpenRouter key, one per provider (`ai_keys`, `encryptedText`, verified by one call before it is stored, each with an `enabled` switch; `account.aiKey.list` returns only providers, switches and last characters). **Enabled keys are ordered by when they were connected**: a picked model runs on its provider's key, else on the OpenRouter one (`chatKeyFor`); Auto and every helper call (titles, suggestions, compaction, web search, the judge) run on the first key. While any key is enabled the chat never falls back to Tamery's account, so every call it makes is an own-key call. **A key runs the chat only** (every procedure behind `ai.chat.use`: the stream, titles and suggestions, compaction, web search, the approval judge, dictation); query edits and fixes, completions, filters and connection diagnosis always run on Tamery under the plan's rules. Chat procedures get the key through `payForAi` (`apps/api/lib/ai-key.ts`), which returns `keys` and the first as `key`, with a `telemetry(scope)` that records a keyed call as `ownKey` (`ai_usage.own_key`), so AI usage lists it at an estimated cost while it never counts toward Pro's budget nor spends credits; they pass `key` (the chat step, the one `pickChatModel` returns) and pick models through `modelsFor`/`chatModelFor` (`packages/ai/models/own-key.ts`), which map the OpenRouter chat ids to the provider's own (Anthropic: dots become dashes). An OpenRouter key runs exactly Tamery's models, fallbacks and Jev on the user's account (Jev's usage goes through the payer's `recordJev`, which records it as `ownKey` too); Jev needs OpenRouter, so another provider's key skips it (Auto is its `OWN_KEY_AUTO_MODELS`, the judge goes straight to its fast-model fallback). Dictation runs on the pick from the keys' `getDictationModels` (`@tamery/shared/ai-key`, picked per device in Settings → AI and sent as `model`, the first one's default when none offers it): OpenAI's speech-to-text models through `transcribe`, Google's and OpenRouter's chat models reading the recording through `generateText` (`dictationFor`). Keys with none (Anthropic alone) are refused, never moved to Tamery's bill. `getPermissions` takes `hasAiKey`, which opens only `ai.chat.use` on Free; buying credits stays Pro's (`ai.credits.buy`).
- Chat and AI-key verification errors surface generic. A caught provider failure is logged through `logProviderError` (`packages/ai/provider-error.ts`): the operation, the error's type and the HTTP status, never the error itself, whose message, stack and fields can carry request and response bodies.
- **A stream lives in the memory of the instance that claimed it.** Other instances join and stop it over Redis pub/sub, so any number of instances can serve a chat, but its chunks die with that instance. A later `ai.attachStream` finds no answer from it and starts the turn again, which spends a model call.
- **Tools run in the window, never on the server**: connections, their strings and the query runtime live in the renderer, so `chatTools` (`@tamery/ai/tools`) have no `execute`. A step that calls tools ends the stream; the window answers each call (`onToolCall`, through `core/agent`), and `sendAutomaticallyWhen` sends the assistant turn back once every call has an output. That turn is the wire's "new turn": `ai.stream` takes only the tool outputs from it (`persistToolOutputs` fills tool parts the model made, matched by call id; the text, steps and usage stay as the server wrote them), the model's reply after the tools extends the same message (`persistMessage` grows parts by order), and it is never a re-ask. **The chat is Pro only (or a user's own key, see Own keys), and Pro's AI spends the included budget, then AI credits** (`apps/api/lib/credits.ts`): a month of model calls, every AI feature together, may cost `PRO_INCLUDED_AI_USD` (`@tamery/shared/credits`), summed from `ai_usage.cost` since the paid period started (at most 30 days back; a trial is a period); past it, each recorded call's overage comes off `credit_accounts.balance`, and an AI call starts only while some budget or balance is left (`credits.canUseAi`; for filters and completions through `usage.enforce`, where Free gets its weekly limit instead). Credits are bought through Checkout, each charge `topUpChargeCents` (the credits plus `CREDIT_TOP_UP.fee`) while the webhook adds only the credits in the payment's metadata; the trial is given only to an account with no earlier Tamery subscription (`mode: 'payment'`, `setup_future_usage: 'off_session'`, so the card stays for auto top-up) and added only by the `payment_intent.succeeded` webhook, once per payment intent (`credit_top_ups` is unique on it). Auto top-up charges the saved card off session when the balance falls under the user's threshold, behind a Redis lock so concurrent calls charge once; a failed charge turns it off rather than retrying a declined card. A user message's steps and tokens are counted from the server's own copy of the answer (its `step-start` parts, the `tokens` the stream writes into its metadata): past either, `chatStream` runs one more step with no tools, which explains where it stopped and marks the answer `capped`, and the chat offers **Continue**, a new user message with a fresh budget. `ask_user` is never answered automatically either: its card holds the agent's questions until the user answers them (`chatToolRuns.reply`, decided once per window like a write), and a new user message instead drops it as an incomplete call. `execute` is never answered automatically: its card waits for **Run** or **Decline**, or, in the chat's **auto** approval mode, presses **Run** itself when `ai.judgeStatement` says so — asked only for a statement `additiveOnly` admits (INSERT and CREATE, no upsert or OR REPLACE; Mongo inserts and creates), so a change to existing data always waits — so a pending change survives a reload as a persisted `input-available` part, and a window decides each call once (`chatToolRuns.write`), whichever card was pressed. The model context is built with `ignoreIncompleteToolCalls`, so a call that never got an output (a window closed mid-run, a change left undecided before the next question) drops out instead of failing every later turn. Every tab attached to a stream answers its read calls, and both send the turn back; one-starter keeps that to one answer.
- **Subagents are child chats run by the window**: `spawn_agent` is answered like a read — `spawnSubagent` (`modules/chat/subagents.ts`) creates a chat whose first `ai.stream` turn carries `subagent: { parentChatId, title }`, sends the task on the model the call names (`model`, any chat model; unset is the user's pick) for every turn of the child, and resolves the call with the child's final text once a finished stream's last step has no tool calls. `ensureChat` stores `parentChatId` only under a top-level chat of the same user and resource, so subagents are one level deep, and `streamChatStep` offers a subagent every tool but `ask_user` and `spawn_agent` and tells it to report back. The child's changes wait for Run in its own view; stopping the parent stops its children. The parent's call output holds the child's chat id, so finished subagents are found from the transcript after a reload; a subagent still running when the window closes is dropped with the parent's incomplete call.
- **One step, every caller**: `streamChatStep` (`features/chat-step.ts`) is the agent's step — instructions, tools, turn limits, prompt caching (the system message and OpenRouter's request-level breakpoint) — and both `chatStream` and the eval (`packages/evals`) run it; the features barrel connects to Redis on import, so the eval imports the file directly.
- **What a tool reads is data, never instructions**: `chatTools`' `toModelOutput` and MCP's tool results put `UNTRUSTED_DATA_NOTE` (`@tamery/shared/mcp`) before every database result and every earlier chat (`search_chats`/`read_chat`, answered from the window's own collections, whose text repeats what those chats read), and both instructions say so. It is a framing, not the guard: the guard is that `chatToolRuns.answer` never runs `execute`, so no text a model read can run a write to the user's database without **Run**; everything else it answers only reads the database or writes to Tamery's own data (drafts, schema notes), except `web_search`, whose query leaves Tamery: the window answers it through `ai.webSearch` (`searchWeb`, OpenRouter's `web_search` server tool on the Exa engine on `models.search`, which returns each page's own address and title; an own Google key's grounding redirects are opened for the page and title they lead to), the tool and the instructions forbid database content in the query, and its result goes back under `UNTRUSTED_WEB_NOTE`. `ai.webSearch` records its cost against the chat, so only the caller's own chat is accepted. Auto mode moves that **Run** to a judge, so the judge is held to the same bar: `ai.judgeStatement` takes the user's request from the stored transcript, never from the client, checks the statement against it with Jev (`typesafe/jev-1.14` on OpenRouter's decisions endpoint, auto-run at a pinned probability threshold) and falls back to `models.fast`; a judge that cannot answer leaves the change to the user. Jev is outside the AI SDK, so every Jev call (the judge, Auto's rating) records its usage with `aiUsage.recordPriced` from the price it reports.
- **Attachments and dictation**: a user turn's files arrive as `file` parts with base64 data URLs, and `ai.stream` moves each into the attachments bucket (`apps/api/lib/attachments.ts`, Bun's S3 client on a GCS bucket under its own KMS key, `infra/attachments.tf`; `s3mock` in dev) under `chats/<chatId>/<id>`, storing an `attachment:<chatId>/<id>` reference in the transcript in its place, so the synced transcript never carries the files. `loadMessages` puts every reference back as a data URL, the only form a model is sent, and the window shows one through `ai.attachment` (the chat's owner only, never gated by `ai.chat.use`). `ai.stream` rejects a turn with more than `CHAT_LIMITS.attachments`, a type outside `attachmentTypes`, or a URL that is neither a data URL nor a stored reference of the same chat (an edited or re-asked turn resends its references), since a remote one would have the model provider fetch it for the user. A chat's files are erased only with its deleted copy, by the purge job, so a dropped turn's files stay until then; older transcripts keep their data URLs. `streamChatStep` counts each file as a fixed token cost when fitting the context, never its base64. `ai.transcribe` takes dictation as 16-bit mono WAV at `DICTATION.sampleRate`, at most `DICTATION.seconds` long (OpenRouter takes no WebM, the only audio Chromium records, so the window converts), and transcribes it with `models.transcribe`. The desktop grants the microphone to the app's own page and audio only (`restrictPermissions`), and `todesktop.json` carries `NSMicrophoneUsageDescription`, without which macOS kills the app on first access.
- **The chat acts as the signed-in user**: it lists the active workspace's connections and ignores MCP's per-connection access, which is MCP's alone.
- **Client**: one `Chat` instance memoized outside React per chat id — identity never changes under a running send. `useChat` holds only the live exchange; settled turns come from the collections, merged by id, the copy with more parts winning and the live one on a tie: a message only grows, and a live tool output lands before its row does. So a chat reopened from the collections has no live turns and `regenerate()` would throw — Retry re-sends the last user message under its persisted id, which the server reads as a re-ask. The SDK's mount-only `resume` option is not used: every tab attaches whenever the merged transcript ends on a user turn and the instance is idle, so a turn started in one tab streams into all of them. Re-entry is self-limiting. The transport maps an empty `attachStream` body to `null`, the SDK's "no active stream" signal — an empty stream would instead run the full request lifecycle (submitted flash, phantom finish).

## Secrets / environment

- **Logs go through `sanitizeLogData`** (`@tamery/shared/sanitize-log`), and a driver's `error` event through `logDriverError`, never a bare `console.error`: pg-pool hands its listener the client, which Bun prints with its non-enumerable `password`. Better Auth's `logger` and every alert email's error text go through it too: a failed Drizzle query carries its bound values, session tokens included, in its message and `params`, and Postgres repeats them in the driver error's `detail`.
- **A secret or signature a caller sends is compared through `safeEqual`** (`apps/api/lib/safe-equal.ts`), never a bare `timingSafeEqual`, which throws on a length the caller picks.
- **Credentialed origins are listed, never matched by suffix.** The session cookie covers every `*.tamery.app` host, so the API's and the proxy's CORS and Better Auth's `trustedOrigins` name exact sites from `@tamery/shared/origins`: a script on any other subdomain (docs, a download host, a dangling DNS record) would otherwise read `connections.list`. The share site renders other people's rows, so the API refuses its origin. CORS only hides the answer, though: a form on any subdomain still posts with the cookie, and oRPC takes a multipart body as input, so the API's `/rpc/*` and the proxy's `originMiddleware` refuse a cookie-carrying request from any origin outside the list (the desktop app sends `x-desktop`, which a page cannot without a preflight). A new site that calls the API from the browser is added there.
- Each app's `env.ts` validates env vars with ArkType. In development, service URLs default dynamically via portless (`monorepo.md`) — don't add them back to `.env`.
- **In production the two wrapping keys live in Secret Manager**, encrypted by a Cloud KMS key (`infra/secrets.tf`), and reach the API's service account as plain env at instance start; no app code touches KMS. Reading a secret needs no KMS role, because Secret Manager's service agent uses the key, so revoking that agent's binding stops every new instance from booting. Dev/test keep plaintext `*_SECRET` in `.env`. Operator steps (setting a value, rotation, recovery): `apps/api/SECRETS.md`.
- **Rotating a wrapping key's value is a keyring** (`packages/db/utils.ts`): `ENCRYPTION_SECRET`/`USER_KEY_SECRET` may hold a comma-separated list, current key first (so a key itself never contains a comma), each key at least 32 characters (`packages/db/env.ts` refuses to load otherwise) — new rows encrypt under the current key, every key is tried on decrypt (AES-GCM's tag rejects the wrong ones). Rotation goes straight to `new,old`, accepting that during the deploy overlap an instance still on the old keyring fails to read the few rows a new instance just wrote; a retired key's offline copy outlives every database backup holding rows under it. Steps: `apps/api/SECRETS.md` → Rotation. The ciphertext format is unchanged, so rows written before the keyring need no migration.
- **Run the rotate scripts through `bun run rotate:*`** in `apps/api`, as the `api-rotate` Cloud Run Job on the API's image and service account, so no secret passes through a shell; dry-run by default, `--execute` applies. `encryption-secret.ts`/`user-key-secret.ts` re-encrypt every column a wrapping key protects, and its copies in `deleted_records`, under its current key with no wrapping transaction — under the keyring a half-done run is a valid state, so an interrupted run is just repeated. `connection-keys.ts` rotates a workspace's (or every workspace's) key — the inner connection-string layer — with no env change or redeploy, minting a fresh key and re-encrypting that workspace's key row, connections and their `deleted_records` copies together per transaction.
- Connection strings are encrypted per **workspace**, not per requester or owner: each workspace's key is a random secret in `workspace_encryption_keys`, wrapped at rest by `USER_KEY_SECRET` via `encryptedTextColumn(env.USER_KEY_SECRET)`, so every member decrypts with the same key and it survives any member leaving or deleting their account. Each workspace's key is created in the transaction that creates the workspace (`workspaceEncryptionKey.create`, `apps/api/lib/encryption-key.ts`), and `workspaceEncryptionKey.get` throws when it is missing rather than minting one, which would leave the stored strings undecryptable; every decrypt path passes the row's own `workspaceId`. Nothing caches a key, so a rotation reaches every instance at once. Every write of a string (create, edit, move, a guest's adoption) reads its key with `workspaceEncryptionKey.getLocked` inside its transaction, after locking the connection row, and `rotate:connection-keys` locks the rows, then the key, then reads the rows again, so no write lands under a key the rotation is replacing and the two never deadlock. A workspace delete cascades the row into `deleted_records` (architecture.md → Deleted records), whose purge crypto-shreds the strings; deleting a user drops the workspaces they were the only member of (`databaseHooks.user.delete.before`).

# oRPC routers, secrets, and environment

## oRPC

- Copy the shape from a neighbouring router in `apps/api/orpc/routers/` and register it in `routers/index.ts`. `authMiddleware` puts `user`/`session` on context; `accountMiddleware` does the same and rejects guests (`FORBIDDEN`); `permissionsMiddleware` adds `context.permissions` (`architecture.md` → Permissions). Clients call through the generated `ORPCRouter` type, never a manual fetch.
- `apps/api` is a composite project whose emitted `.types` are what clients type-check against: after changing a router, run `tsc` in `apps/api` before `check-types` elsewhere, or clients check against the old contract.
- `create` and `remove` procedures take exactly one item — never `type.or(schema, schema.array())`; the offline outbox sends one row per call.
- **No `.output()` schemas** — the handler's inferred return type already is the client contract; an output schema only duplicates it and re-validates the server's own data on every call. The exception is a schema that also types something else — the sync collections' Redis publisher, `banner`'s accumulated items.
- **Errors are declared, not constructed**: a procedure or middleware lists its codes in `.errors({ CODE: { message } })` and throws `errors.CODE()`, so the code and its message live in the contract the client is generated from. `new ORPCError(...)` only where no `errors` map exists — handler interceptors and helpers outside a procedure. Clients narrow with `isDefinedError`.
- **`internal.*` is the proxy's API**, gated by `proxySecretMiddleware` (`x-proxy-token`). `internal.shares.resolve` is the one path that hands out a decrypted connection string without a user session, so it refuses an expired share or one whose connection is no longer synced with Full, and checks the password before decrypting. Every password attempt is rate limited in Redis (`@orpc/ratelimit`) per share and viewer network (the proxy's `cf-connecting-ip` through better-auth's `normalizeIP`, so an IPv6 viewer counts by its /64) with a far higher share-wide cap behind it, and is counted before verifying: counting only failures after a slow argon2 verify lets parallel guesses all pass. Keying by viewer keeps a stranger's guesses from locking everyone else out; the share-wide cap keeps a guesser with many addresses bounded. A right password answers with an unlock token (an HMAC over the share id and its password hash), which the share site keeps in an httpOnly cookie and sends instead of the password, so a page load never runs argon2 and changing the password turns every earlier viewer away.
- **A proxied query checks its session once.** `internal.proxy.resolveConnectionString` runs `authMiddleware` and, when the proxy sends `withUserId`, answers with the session's `userId` beside the string, and the proxy takes that as the query's owner, so a query by connection or resource costs that one API call and no `/auth/get-session` of its own. Only a raw connection string and a transaction step, which never reach the API, check the session through `/auth/get-session`. No session cache in the proxy: it would keep a revoked session working until the entry expired. The API and the proxy deploy in parallel and roll back one at a time, so the API still answers a caller that does not ask with the bare string, and the proxy falls back to `/auth/get-session` when an API without `withUserId` does the same.
- **A sign-in challenge (`account.challenge.*`) is handed a session only for a device that asked for it.** Whoever holds the verifier gets the session, so anyone can mail a victim a confirm link for their own challenge: the desktop app and the CLI open the browser only after their own `listen` registered the challenge with its IP and User-Agent, and `publish` refuses one nobody registered. The attacker's own device registers too, so against a mailed link only the confirm page's warning and the new-sign-in email stand: the page shows no device or code to compare. `newUser` is decided on the server from the account's age, since a client-sent flag would also switch off the new-sign-in email. The web app signs in with the site's cookie and never exchanges, so `type=web` only lands on `/open`.
- **The new-sign-in email goes only to a device the account has not signed in from.** A device is the versionless browser + OS and the IP's city, kept per user in Redis for 180 days and recorded at sign-up too; so an attacker on the same browser, OS and city as the victim gets no email. A Redis failure counts as a new device.
- **An error passed through the proxy keeps its type only if the proxy declares it too.** oRPC marks a rethrown error as defined only when the procedure's own `.errors()` lists its code, so the API's `internal.shares.resolve` and the proxy's `shares.*` spread the same maps from `@tamery/shared/share`, and the share site reads them with `safe()`'s `definedError` instead of matching code strings.
- `syncDiff` diffs in memory: a router gives it `versions` (the id and `updatedAt` of every row the user may see, a light indexed read) and `rows` (full rows for the ids that changed), never a query per client row or a parameter per id. A client sends every id it holds on each reconnect, so ids go to Postgres as one array through `idIn`: `inArray` binds one parameter per id and Postgres refuses past 65535.
- **Work that outlives its response goes through `runInBackground`** (`@tamery/shared/background`), since SIGTERM waits for it up to `DRAIN_LIMIT_MS` (`apps/api/lib/shutdown.ts`). Cloud Run kills the instance 10 seconds after SIGTERM, so the limit stays under that. Sync publishes stay unawaited and untracked: Redis queues commands while offline, so awaiting one would hang the write through an outage, and closing the client at shutdown sends what is queued.
- **A Stripe call made while a transaction holds a lock is bounded**: it passes `STRIPE_UNDER_LOCK` (`apps/api/lib/stripe.ts`, 15 s and one retry), the transaction runs `LOCK_TIMEOUT` (5 s) before taking the lock, and an error `timedOutUnderLock` recognizes answers a retryable error. With the client's defaults (80 s, 2 retries per call) a slow Stripe would hold the lock and a pool connection for minutes, and every waiter with it.

## Chat

- Stack: AI SDK (`ai` v7 + `@ai-sdk/react`) + OpenRouter (`@openrouter/ai-sdk-provider`, the only model provider package) + `ai-retry` (cross-model fallbacks) + `ai-resumable-stream` (Redis). Not `@tanstack/ai`.
- `ai.stream`: the wire carries only the new turn; the stored transcript is the model context, so a client can never send stale history. Titles generate server-side beside the first answer. **The step offers no tools yet**: no window answers a tool call, so `streamChatStep` runs the plain assistant instructions with none.
- `ai.attachStream` answers "what should be streaming into this chat right now" — the live stream when one exists (a pointer per chat, not per device), else a fresh stream when the transcript ends on a user turn that never concluded, decided once on the server. A turn that ended carries its own evidence (answered and failed turns persist an assistant message, a stopped one flags the user message), so only a crash mid-stream is eligible for the restart. Empty is nothing to stream, never an error. Deliberately not named `resume` — it can spend a model call.
- `ai.abortStream` publishes stop through Redis and flags the user turn stopped before it returns, so no tab re-attaches to a turn the user stopped; a client that merely leaves stops nothing.
- No output schemas on streaming procedures (the chunk union belongs to `ai`), and `ai.stream`'s `messages` schema stays loose — `validateUIMessages` is the real check.
- **Never wire the request signal into `streamText`** — streams are detached on purpose; only `chatStream.stop` aborts. A reload is not a cancellation.
- **One turn per chat, claimed first**: `chatStream.begin` sets the chat's Redis pointer with **NX** to `setup:<id>` before the turn is stored, paid for or prepared, in `startChatTurn` (`apps/api/lib/chat/turn.ts`), which `ai.stream` and `ai.attachStream`'s restart share. A request that loses writes and pays for nothing and resumes the winner's stream, so two tabs racing one turn watch one answer; `resume` waits out a turn still in setup. **`stop` during setup swaps the pointer to `stopped:<id>`** and keeps the chat claimed: the setup checks `stopped()` before it pays for more, flags only its own user message stopped and frees the claim itself, and a new turn waits that pointer out. **`start` registers the stream before it swaps `setup:<id>` for the stream id**, so a resume never finds a pointer to a stream that does not exist yet; a swap that finds the pointer changed streams nothing. `CONFLICT` is only for a pointer whose stream is already gone. The pointer is released on flush, a failed setup or a failed resume; a setup pointer expires after five minutes, a stream's after an hour.
- **Ids are the idempotency**: the user turn's uuid v7 is minted client-side and is the row id (a re-ask lands on `onConflictDoNothing`); assistant ids are minted server-side. A re-ask therefore leaves the transcript ending on an assistant turn — that is what a regenerate looks like on the wire, so `ai.stream` deletes that answer before building the model context instead of asking the model to continue it. The UI stream's `onEnd` persists the assistant row, and the stream only ends once `onEnd` settles, so the resumable Redis stream stays open until the row lands: a reload mid-finish rejoins or finds the row, never neither. Keep the persist inside `onEnd` (awaited), not in a detached callback.
- **`@tamery/ai` vs `apps/api` splits by dependency, not topic**: db/auth/oRPC stays in the app; models and stream lifecycle live in the package; persistence is handed in as `onFinish`. Provider fallbacks live only in the package's model list.
- **Usage**: capture is the package's, the row is the app's. `createAiUsage(onRecord)` hands persistence in the way `chatStream` takes `onFinish`, and returns `telemetry(scope)`, a per-call AI SDK telemetry integration, **not** a global registration and no ambient context. Pass it as the `telemetry` option of any model call and that call reports itself, with the `modelId` that actually answered, so an `ai-retry` fallback is reported as itself; a closure beats async context for a detached stream, and a call passing no telemetry records nothing. A call made outside the AI SDK (Codestral's fill-in-the-middle fetch) reports through the returned `record(scope, modelId, usage)`. **Structured output goes through `generateText` with `Output.object`, never `generateObject`**: it is deprecated in this SDK and skips the model-level hook, so nothing would be recorded. **Aborted streams record nothing and cannot**: the provider never sends a finish chunk, so no token counts exist. **An output schema has no optional keys**: `@tamery/shared/arktype-config` turns `exactOptionalPropertyTypes` off, so `'key?'` becomes `T | undefined`, which has no JSON Schema form and fails every call at runtime (`ToJsonSchemaError`); make the key required and `| null`.
- Errors surface generic. A caught provider failure is logged through `logProviderError` (`packages/ai/provider-error.ts`): the operation, the error's type and the HTTP status, never the error itself, whose message, stack and fields can carry request and response bodies. A procedure that calls a provider outside the chat stream catches its failure and answers a fixed error.
- **Cost**: a call through OpenRouter is recorded at the cost OpenRouter reports, plus the provider's own bill (`costDetails.upstreamInferenceCost`) when the provider runs on Tamery's own key (BYOK), where OpenRouter's `cost` is only its fee and often 0; a call OpenRouter reports no cost or a total of 0 for, or any other call, is priced by `getModelCost` from LiteLLM's table, trying the id, its bare name with dots as dashes and the provider without dashes (`xai/…`); a call that spent tokens and still has no cost is stored with no cost, so it spends no credits, and `apps/api/lib/ai-usage.ts` logs it and emails an Alert to `ALERTS_EMAIL`, so a model priced elsewhere (Codestral, under `mistral/`) is recorded with that prefix. `packages/ai/scripts/economics.ts` estimates a Free, Pro and trial month from the real prompts, `AI_QUERY_LIMITS`, `MODEL_IDS`, `FREE_WEEKLY_LIMITS`, `CHAT_LIMITS` and `PRO_PRICE_USD`; any change to a model, a prompt, an input cap, a limit or a price runs `bun run economics` in `packages/ai` before and after and reports the cost per call and Pro's margin, and `scripts/economics.test.ts` holds the budget, never raised without saying what it costs.
- **Own keys (BYOK)**: a user may save an Anthropic, OpenAI, Google and OpenRouter key, one per provider (`ai_keys`, `encryptedText`, verified by one call before it is stored, each with an `enabled` switch; `account.aiKey.list` returns only providers, switches and last characters). **Enabled keys are ordered by when they were connected**: a picked model runs on its provider's key, else on the OpenRouter one (`chatKeyFor`); Auto and every helper call (titles, suggestions, compaction, web search, the judge) run on the first key. While any key is enabled every chat call runs on one of them, never on Tamery's account, so each is recorded as `ownKey` (`ai_usage.own_key`): AI usage lists it at an estimated cost while it never counts toward the budget nor spends credits. **A key runs the chat only** (every procedure behind `ai.chat.use`); query edits and fixes, completions, filters and connection diagnosis always run on Tamery under the plan's rules. **Only `aiPermissionsMiddleware` reads the keys**, once per request for both `ai.chat.use` and the payer, so a procedure that checks `ai.chat.use` uses it: `permissionsMiddleware` reads none, which keeps a query off every other request. An OpenRouter key runs exactly Tamery's models, fallbacks and Jev on the user's account (Jev's usage goes through the payer's `recordJev`, recorded as `ownKey` too); Jev needs OpenRouter, so another provider's key skips it (Auto is its `OWN_KEY_AUTO_MODELS`, the judge goes straight to its fast-model fallback). Dictation runs on the pick from the keys' `getDictationModels` (`@tamery/shared/ai-key`, sent as `model`, the first one's default when none offers it) through `dictationFor`; keys with none (Anthropic alone) are refused, never moved to Tamery's bill. `getPermissions` takes `hasAiKey`, which opens only `ai.chat.use` on Free; buying credits stays Pro's (`ai.credits.buy`).
- **Who pays, and the budget** (`apps/api/lib/credits.ts`): every procedure Tamery may pay for runs `paidAiMiddleware` (`apps/api/orpc/index.ts`), and `usage.metered`'s unlimited branch and `ai.attachStream`'s restart call the same `payForAi`: the user's keys, else Tamery only for an active plan with budget or credits left, else `TOO_MANY_REQUESTS` with `AI_BUDGET_SPENT_MESSAGE`. Free's weekly-limited features are Tamery's own cost and spend nothing. A plan's month of model calls, every AI feature together, may cost `PRO_INCLUDED_AI_USD` (`@tamery/shared/credits`), summed from `ai_usage.cost` since the paid period started (at most 30 days back; a trial is a period). **`credits.settle` records every call**, and for a plan's Tamery-paid call takes the overage it adds past the budget off `credit_accounts.balance` in one transaction locked on the account row, so parallel calls settle one after another and each pays only its own share. Without credits the balance goes below zero, and that debt refuses Tamery-paid AI, a new period included, until credits cover it. A user runs at most `PAID_CALLS_AT_ONCE` Tamery-paid calls at once (`credits.hold`), chat turns and every other AI call together, which bounds what calls in flight can cost before they settle: `paidAiMiddleware` and `usage.metered`'s unlimited branch hold a slot while the call runs (`credits.inPaidSlot`), and a chat turn holds one under its turn id while it streams.
- **AI credits** are bought through Checkout (`account.credits.topUp`, Pro only, returning through `billingDestination`), each charge `topUpChargeCents` (the credits plus `CREDIT_TOP_UP.fee`), with `setup_future_usage: 'off_session'` so the card stays for auto top-up. The `payment_intent.succeeded` webhook adds them once per payment intent (`credit_top_ups` is unique on it), and only when the USD received is that charge; a manual top-up's card becomes the one auto top-up charges. **Auto top-up runs one attempt at a time**: when a settle leaves the balance under the threshold it stores `auto_top_up_attempt_id`, charges that card off session with the id as Stripe's idempotency key, and only that charge's success or failure clears it; a failed charge turns auto top-up off rather than retrying a declined card. Turning it on needs Pro and a top-up's card, turning it off needs neither, and its threshold stays under its amount. `charge.refunded` and `charge.dispute.created` take the refunded or disputed share back once (`credit_top_ups.reversed`), even below zero, and a won `charge.dispute.closed` gives back all but the refunded share; `charge.dispute.created` goes by the dispute's live status, so one replayed or late after a win takes nothing. One that arrives before its payment is credited fails for a credits payment, so Stripe sends it again. The events the endpoint must send are listed in `apps/api/SECRETS.md`.
- **The approval judge reads only the server's copy**: `ai.judgeStatement` takes the chat and the `execute` call's id. The statement comes from that stored `input-available` call (it waits a few seconds for the step that made the call to be stored), the dialect and the `additiveOnly` risk from the chat's own connection, the only one a change may target, and the request, the answers to `ask_user` and the proposal from the stored transcript. `persistToolOutputs` takes only a tool part's output and state from the window, never its input, so the judged call is the one the model made. It runs behind `paidAiMiddleware` and a per-user rate limit; a refusal or failure leaves the change to the user.
- **Schema notes are data**: the agent saves a note without asking, from what it read in the database, so `formatSchemaNotes` puts every note in a section that says it is never an instruction, and a note is at most `SCHEMA_NOTE_LIMIT` characters (the tool and both routers).
- **A chat's attachments live under its id and its server-set `createdAt`** (`chatAttachmentsPrefix`): the id is client-minted and may repeat a deleted chat's, so the creation time keeps a new chat off the old files, and the purge, which reads `createdAt` from the deleted copy, off the new ones.
- **Compaction**: a chat's `compaction` (encrypted, synced, never writable through `chats.update`) is a summary standing in for every message through `throughMessageId`; `ai.stream`/`ai.attachStream` send the model only what follows it, with the summary in the instructions. A new user turn compacts first when the rest would fill `COMPACT_AT` of the resolved window, and `ai.compact` does it on demand; both summarize only what precedes the last user message, so a turn in progress keeps its own messages and its tool steps never lose their context. The summary runs on `models.summary` (a 1M-window model, since it reads up to a full window) and is recorded as chat usage. `fitContext` stays as the backstop for a single turn larger than the window.
- **A chat file reaches the model only while it is fresh** (`apps/api/lib/chat/attachments.ts`): every file of the latest message the user wrote, and those of the `FRESH_ATTACHMENTS.turns` before it within its byte budget (a SQL run or Continue is no turn), every other one a line naming it, so a long chat does not resend every screenshot each turn. **Only the chat stream and compaction read the transcript through `forModel`**; title, suggestion, Auto and the approval judge read the stored one, where a file is never text, so a PDF's content can never pass for the user's words; the PDF text the model reads is framed with `UNTRUSTED_FILE_NOTE`. `store` writes the file as sent; `copy` makes the model's smaller copy beside it in the background, one at a time per instance and within `MODEL_COPY_TIMEOUT_MS`, so parsing never delays the first token, and a file goes as sent until its copy exists. In production a fresh file goes as a signed link to the public `/attachments` route, which keeps the request small and the transcript prefix the same across turns; whether a provider's cache reuses it across turns is not measured. The signature is the link's only credential: it expires two to three weeks out, rounded to a week so the link stays stable, its key comes from the `ENCRYPTION_SECRET` keyring (current key signs, any key opens), and the route answers only while the file is still a part of a user message in the chat. Never log or alert with a request's query.
- **A stream lives in the memory of the instance that claimed it.** Other instances join and stop it over Redis pub/sub, so any number of instances can serve a chat, but its chunks die with that instance. A later `ai.attachStream` finds no answer from it and starts the turn again, which spends a model call.
- **Client**: one `Chat` instance memoized outside React per chat id — identity never changes under a running send. `useChat` holds only the live exchange; settled turns come from the collections, merged by id, persisted rows winning. So a chat reopened from the collections has no live turns and `regenerate()` would throw — Retry re-sends the last user message under its persisted id, which the server reads as a re-ask. The SDK's mount-only `resume` option is not used: every tab attaches whenever the merged transcript ends on a user turn and the instance is idle, so a turn started in one tab streams into all of them. Re-entry is self-limiting. The transport maps an empty `attachStream` body to `null`, the SDK's "no active stream" signal — an empty stream would instead run the full request lifecycle (submitted flash, phantom finish).

## Secrets / environment

- **Logs go through `sanitizeLogData`** (`@tamery/shared/sanitize-log`), and a driver's `error` event through `logDriverError`, never a bare `console.error`: pg-pool hands its listener the client, which Bun prints with its non-enumerable `password`. Better Auth's `logger` and every alert email's error text go through it too: a failed Drizzle query carries its bound values, session tokens included, in its message and `params`, and Postgres repeats them in the driver error's `detail`.
- **A secret or signature a caller sends is compared through `safeEqual`** (`apps/api/lib/safe-equal.ts`), never a bare `timingSafeEqual`, which throws on a length the caller picks.
- **Credentialed origins are listed, never matched by suffix.** The session cookie covers every `*.tamery.app` host, so the API's and the proxy's CORS and Better Auth's `trustedOrigins` name exact sites from `@tamery/shared/origins`: a script on any other subdomain (docs, a download host, a dangling DNS record) would otherwise read `connections.list`. The share site renders other people's rows, so the API refuses its origin. CORS only hides the answer, though: a form on any subdomain still posts with the cookie, and oRPC takes a multipart body as input, so the API's `/rpc/*` and the proxy's `originMiddleware` refuse a cookie-carrying request from any origin outside the list (the desktop app sends `x-desktop`, which a page cannot without a preflight). A new site that calls the API from the browser is added there.
- Each app's `env.ts` validates env vars with ArkType. In development, service URLs default dynamically via portless (`monorepo.md`) — don't add them back to `.env`.
- **In production the two wrapping keys live in Secret Manager**, encrypted by a Cloud KMS key (`infra/secrets.tf`), and reach the API's service account as plain env at instance start; no app code touches KMS. Reading a secret needs no KMS role, because Secret Manager's service agent uses the key, so revoking that agent's binding stops every new instance from booting. Dev/test keep plaintext `*_SECRET` in `.env`. Operator steps (setting a value, rotation, recovery): `apps/api/SECRETS.md`.
- **Rotating a wrapping key's value is a keyring** (`packages/db/utils.ts`): `ENCRYPTION_SECRET`/`USER_KEY_SECRET` may hold a comma-separated list, current key first (so a key itself never contains a comma), each key at least 32 characters (`packages/db/env.ts` refuses to load otherwise) — new rows encrypt under the current key, every key is tried on decrypt (AES-GCM's tag rejects the wrong ones). Rotation goes straight to `new,old`, accepting that during the deploy overlap an instance still on the old keyring fails to read the few rows a new instance just wrote; a retired key's offline copy outlives every database backup holding rows under it. Steps: `apps/api/SECRETS.md` → Rotation. The ciphertext format is unchanged, so rows written before the keyring need no migration.
- **Run the rotate scripts through `bun run rotate:*`** in `apps/api`, as the `api-rotate` Cloud Run Job on the API's image and service account, so no secret passes through a shell; dry-run by default, `--execute` applies. `encryption-secret.ts`/`user-key-secret.ts` re-encrypt every column a wrapping key protects, and its copies in `deleted_records`, under its current key with no wrapping transaction — under the keyring a half-done run is a valid state, so an interrupted run is just repeated. `connection-keys.ts` rotates a workspace's (or every workspace's) key — the inner connection-string layer — with no env change or redeploy, minting a fresh key and re-encrypting that workspace's key row, connections and their `deleted_records` copies together per transaction.
- Connection strings are encrypted per **workspace**, not per requester or owner: each workspace's key is a random secret in `workspace_encryption_keys`, wrapped at rest by `USER_KEY_SECRET` via `encryptedTextColumn(env.USER_KEY_SECRET)`, so every member decrypts with the same key and it survives any member leaving or deleting their account. Each workspace's key is created in the transaction that creates the workspace (`workspaceEncryptionKey.create`, `apps/api/lib/encryption-key.ts`), and `workspaceEncryptionKey.get` throws when it is missing rather than minting one, which would leave the stored strings undecryptable; every decrypt path passes the row's own `workspaceId`. Nothing caches a key, so a rotation reaches every instance at once. Every write of a string (create, edit, move, a guest's adoption) reads its key with `workspaceEncryptionKey.getLocked` inside its transaction, after locking the connection row, and `rotate:connection-keys` locks the rows, then the key, then reads the rows again, so no write lands under a key the rotation is replacing and the two never deadlock. A workspace delete cascades the row into `deleted_records` (architecture.md → Deleted records), whose purge crypto-shreds the strings; deleting a user drops the workspaces they were the only member of (`databaseHooks.user.delete.before`).

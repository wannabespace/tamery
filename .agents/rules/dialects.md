# Database dialects

Six SQL dialects and MongoDB behind one UI: `postgres`, `mysql`, `mssql`, `clickhouse`, `sqlite`, `oracle` (`SqlDialect`) and `mongodb` (`Dialect` holds all seven; MongoDB has its own section below). A connection's `type` (`ConnectionType`) is what the user connected to and can be narrower than its dialect (MariaDB); `getDialect(type)` gives the dialect every query runs on, so code that builds or gates SQL takes a `Dialect`, never a `ConnectionType`. Anything under a resource reads `dialect` and `defaultSchema` from the `$resourceId` route context instead of converting `connection.type` again; `getDefaultSchema` resolves the schema (the capability's fixed one, else the login's, else the resource), and the tables list, which runs outside a route, resolves it the same way from its own connection string. A saved string keeps the type's own scheme (`mariadb://`), so parsing it back gives the same type; ClickHouse's is `http://` or `https://`, the URL its own clients take, which no other engine saves. Every `createQuery` supplies all seven — the type demands it, so a new read cannot quietly skip one. A dialect that cannot express the statement gets `unsupported('<Feature>')` from `@tamery/shared/unsupported`, never a hand-thrown `Error`, so the message reads the same everywhere.

**A write is a `createQuery` too** — raw `sql` executed per dialect, `unsupported(feature)` for the engines that cannot write it. Each dialect spells out its own execution: no shared wrapper stands between the statement and `createQuery`, so a file reads as the statements it runs. One write is one file (`architecture.md`), and a statement two of them share is built in the subject's `shape.ts`, which becomes a `shape/` folder once it would pass the line ceiling — `index.ts` plus a file per split-off statement (`tables/shape/alter-column.ts`). Any query file split for length does the same (`tables/columns/` holds `index.ts` and one catalog reader per engine). **A row query (`core/queries/rows/`) runs one statement every engine spells alike**, so the file builds it once in a local function taking `db` (the page read is `selectPage` in `@tamery/connection/queries/select-page`, which the proxy's share reads compile too), and each entry calls it with the engine's own piece from `shape.ts` — `mssql: (db) => countValues(db, textContains.mssql, params)`; the builder never takes a `Dialect` to re-dispatch on. A row value reaches SQL only through `bindValue[dialect](columnType, value)` there, so the set, insert and delete queries take the table's `columns` and bind internally. The ClickHouse and SQLite entries of the filtered row queries, and the proxy's share reads, pass `filterValueBindings[dialect](columns)` (`@tamery/connection/queries/value-binding`) to `toKyselyFilter`, since a ClickHouse DateTime cannot compare against the ISO text it returns and SQLite stores a boolean as 1 or 0. **A statement the UI shows before running it** (the visualizer's review) is the exception: it is built once, in the subject's shape, as a builder returning a `CompiledQuery` (`<verb>Statement(dialect, db, target)` when the spelling differs per engine, the plain Kysely builder's `.compile()` when it does not), the preview compiles it on a cold dialect and every dialect of the query executes that same builder — so the review shows exactly what runs.

**Every per-dialect capability lives in one table**, `core/catalog/capabilities.ts`: one entry per `Dialect`, so what an engine supports reads top to bottom in one place instead of being spread over a set per feature. The yes/no capabilities are one `flags` array of just the ones the engine has (a `CapabilityFlag`), read with `getCapabilities(dialect).flags.includes('<flag>')`; the typed `readonly CapabilityFlag[]` makes a bad name a compile error, so it is as safe as a boolean field was. Everything with a shape of its own (column types, names, sections, triggers, functions, policies) stays its own keyed field. Column types sit apart in `column-types.ts`, the section gates below in `section-capabilities.ts`. Adding an engine is one entry the `Record` will not let you omit, and a new flag is one more member of `CapabilityFlag`. **A `.tsx` never compares `Dialect`**: a per-engine fact is a capability entry, and a per-engine rule that needs logic (a body template, a grammar restriction, a replace-versus-recreate decision) lives in the subject's `shape.ts` beside the statements it protects.

## MongoDB

MongoDB is the first engine that does not speak SQL, so **anything built on Kysely or `@tamery/sql` takes a `SqlDialect`**, never a bare `Dialect`: the Kysely dialects, `@tamery/sql`'s specs, codegen's SQL, the visualizer, a table share's SQL read (its MongoDB read pages a collection through `mongoPage` instead). Code that only holds a `Dialect` narrows with `isSqlDialect`, which is a language-family check, not a per-engine compare, so a `.tsx` may call it; a SQL-only path a gated UI cannot reach for MongoDB narrows with an `unsupported()` backstop.

- **A statement is checked through `getQueryLanguage(dialect)`** (`core/runtime/language.ts`): splitting, the destructive confirm, the catalog refresh, MCP's read-only check and the code highlighter all go through it, so the runner and MCP never call `@tamery/sql` with a dialect that may be MongoDB. mongosh text holds no transaction statements; a transaction is a session the app opens.
- **A query's `mongodb` entry gets a `MongoDatabase`** (`core/runtime/dialects/mongodb.ts`), not Kysely. Every method writes the mongosh statement it runs, so the query log shows what a user could paste into the runner, and the executor runs nothing but that text. A command takes its name apart from its options (`command('listDatabases', { nameOnly: true })`): the server reads a command's first key as its name, and `sort-keys` would reorder a literal.
- **The executor parses, it never evaluates JavaScript.** `@tamery/mongo/parse` reads the text with acorn into `db` call chains (`db.<collection>.<method>(…).<cursor>(…)`, `getCollection`, `getSiblingDB`, `runCommand`), refuses anything else, and `@mongodb-js/shell-bson-parser` evaluates each argument as a BSON literal. The method tables in `@tamery/mongo/methods` are the one list the executor runs, the editor completes, and the destructive and read-only checks classify; a new method goes there with its effect. A `runCommand` is read-only only for the commands `parse.ts` lists.
- **Values cross every transport as relaxed Extended JSON** (`{ "$oid": … }`), the only form that keeps an ObjectId or Decimal128 its type over IPC and HTTP; `toShell` writes one back as the shell constructor of the same type. The grid shows a top-level field plainly (`fromWire`: an ObjectId as hex, a date as ISO text) and stores an edit as its column's BSON type (`toWire`), so a row query takes the table's columns as the SQL ones do; nested values stay Extended JSON in the JSON editor.
- **A collection's columns are sampled**: `$sample` of 100 documents and each field's `$type`, `_id` first as the identity and the one primary key (`constraints/list/mongodb.ts`), so the grid edits by `_id`. An empty collection samples nothing, so the columns query synthesizes the `_id` column itself — otherwise the grid has no primary-key column and the first insert is unreachable. `declaredColumns: false` hides every column DDL. BSON's internal Timestamp and an always-null field read as JSON, never as a date or text column.
- **Transactions need a replica set or a sharded cluster.** The executor opens a session transaction there and runs the calls one by one on a standalone server, as ClickHouse does; `read only` is enforced by the parser on both. A cancel finds the operation by the query id every call carries as its `comment` and kills it with `killOp`.
- **The cloud proxy routes the driver through a validating SOCKS proxy** (its `guardedForwarding`, `domain.md` → Connection String), not only the seed: it dials every server the driver discovers — a replica set member, SRV target or literal IP among them — only after that host passes the public-address check, which a DNS lookup could not, since the driver skips the lookup for IP literals. `assertReachable` fast-fails the seed up front and skips an SRV name, which has no address of its own.
- App code targets MongoDB 5.0 and up (`hello`, `$objectToArray`, `$facet`, `$sample`); nothing newer may be required by an app query.

## Never offer what the dialect cannot do

**`unsupported()` is a backstop, never a user path.** Reaching one in the UI is a bug in the gating. Gate at the coarsest level that fits:

| Level | Gate | Example |
| --- | --- | --- |
| Whole feature | `getCapabilities(dialect)` | Only Postgres offers CASCADE on a drop |
| Whole section | `sectionAvailable(section, dialect)` | ClickHouse has no Functions or Triggers section |
| Whole operation | `getSectionCapabilities(section, dialect)` | Only Postgres drops an enum |
| One operation | the section's own rule | An index that enforces a constraint, or carries options the picker cannot show, only renames |
| One option in a form | narrow the option list in the table | `referentialActions` drops what an engine lacks |

A section entry carries two states apart: `false` is *no such section* — no list query on this dialect, show nothing; `{}` is *read-only* — the list reads fine and nothing writes. Conflating them hides sections that work.

**A hidden section must be hidden on every route into it.** The navigator filtering its own list is not enough — `$tabId`'s `beforeLoad` re-checks `sectionAvailable` and redirects, so a deep link or a stale bookmark lands on the resource instead of mounting a section whose list query throws.

## Writing the per-dialect statement

- Narrow at the *form*, not in the statement. A statement that quietly rewrites what the user chose is worse than an option they were never offered.
- Prefer one dialect's own syntax over emulating another's. SQL Server swaps a constraint inside a transaction, MySQL does it in a single `ALTER` — that is two implementations of one query, not a shared helper plus branches.
- **A save that needs more than one statement runs them in one `db.transaction()`** — Postgres and SQL Server roll the whole swap back, so a failed `CREATE` leaves the old object standing. MySQL commits DDL implicitly and rolls nothing back, so it is the one engine whose drop-then-create still warns the user, and what fits one `ALTER TABLE` goes in one (a new column and its foreign key; a column's rename, retype and new key). Its trigger and routine recreates read `SHOW CREATE` before the drop and replay it if the create fails, and pass the saved `DEFINER` so a save never hands the object to the editing account. Oracle commits each DDL statement too and refuses a drop and an add in one `ALTER`, so its constraint and index recreates go through `replaceWithSavedDdl` (`shared/definition.ts`), which reads `DBMS_METADATA.GET_DDL` before the drop and replays it if the create fails. A PL/SQL unit that fails to compile is still created, as INVALID, so Oracle routine and trigger saves go through `plsqlUnit.save` (`shared/plsql.ts`): it refuses before any drop when it cannot read the original's `ALL_SOURCE`, reads `ALL_ERRORS` after the `CREATE`, drops a unit it just created or replays the saved source over one it replaced, and throws the compile errors. Those two hold only the read-drop-create-replay order; each entry still passes its own statements.
- **SQL aliases are snake_case** (`c.relrowsecurity as row_level_security`); the query's arktype `type` renames them to camelCase in its `.pipe()`, so a catalog read looks like SQL and the app sees one naming.
- A catalog column only some engines expose belongs in that dialect's schema file under `runtime/dialects/<type>/schema/`, not behind a cast.
- **MariaDB is a `ConnectionType` that runs on the `mysql` dialect**: the type only names and badges the connection (`connectionTypeLabels` in `@tamery/shared/enums/connection-type`, the icon, the engine an AI prompt names). A database that speaks another engine's protocol is added as a `ConnectionType` mapped to that dialect when only its name and a few gates differ, and as a new `Dialect` with its own `DialectSpec` when its SQL differs throughout. A type that lacks something its dialect offers needs the capability gates to resolve by the connection's type rather than its dialect, so the form never offers what it cannot run. A catalog read whose answer differs on MariaDB checks `version() LIKE '%MariaDB%'` in the query, or in a read before it when the difference is a name MySQL lacks. A table or column only MariaDB has is read only after that check says MariaDB, because MySQL fails the whole statement on a name it lacks; its type lives in `MariadbTables` (the mysql dialect's schema), never in the shared schema, so a read reaches it only through `db.$extendTables<MariadbTables>()` and names it only inside the MariaDB branch.
- **A catalog read is Kysely too.** A `CASE` is `eb.case()`, an `EXISTS` is `eb.exists()`, a chain of `OR`s is `eb.or()` — raw `sql` only wraps what no builder spells (a catalog function, bit or array arithmetic, a lateral `unnest`), and a branch that needs one keeps it inside `.then()`. `.then()` here is a case branch, not a promise, so `promise/prefer-await-to-then` is off for `core/queries` and `core/runtime` in `oxlint.config.ts`. Kysely widens a literal branch to `string`/`number`, so a column the read's `type` pins to a union takes `$narrowType` on the query rather than a cast in the select list.
- **`.limit()` and `.offset()` work on SQL Server as written**: its query compiler turns a bare limit into `TOP` and gives an offset without `ORDER BY` an `order by (select null)`, so a query never branches on the engine for paging.
- **A write never retries on reconnect.** `createQuery` reconnects and retries only the queries that declare a result `type` — a read. A lost response to a statement that writes may still have committed, and DDL is not idempotent.
- **Kysely's schema builders first; raw `sql` with `sql.id` only where no builder exists.** `db.withSchema(schema).schema.alterTable(table)` and friends cover table, column, constraint, index, schema, type and view. Raw is for what Kysely cannot spell: function, procedure, trigger, policy, `ALTER INDEX`, an enum value or type rename (`alterType()`'s `renameValue` and `renameTo` type a runtime string as `never`), SQL Server's `sp_rename`, and two actions in one `ALTER TABLE` (MySQL's key swap, a column added with its foreign key). A builder splits a *name* on `.`, so the schema always goes through `withSchema`, never `alterTable('schema.table')`; a table whose own name holds a dot is the accepted edge.
- **SQLite's catalog is the `pragma_*` table-valued functions**, read through `core/queries/shared/sqlite-catalog.ts`: every table-level read starts from `userTables`, which hides SQLite's and D1's own objects (D1 fails a whole read that touches one) and FTS5/R*Tree shadow tables. It stores no constraint names (a key takes its backing index's name, the rest are synthesized), no comments, and a trigger's timing and event only inside its stored `CREATE TRIGGER`, which `triggers/shape.ts` parses. Its DDL names the table unqualified wherever the statement already names a schema elsewhere — `CREATE INDEX "main"."i" ON "t"`, `CREATE TRIGGER … ON "t"`, `REFERENCES "t"` — so those are built in the subject's shape, never through a `withSchema` builder. It changes a stored table only by adding, renaming or dropping a column; everything else is a rebuild Tamery does not run, so `alterColumns: false` and a read-only constraints section gate it.
- **Oracle's dictionary is spelled in upper case.** Kysely quotes every identifier and a quoted Oracle name is case-sensitive, so a catalog read names `ALL_TAB_COLS` and `OWNER`, never `all_tab_columns`, while its snake_case aliases stay quoted lower case and come back as written. The rest of Oracle's spelling is the query compiler's job (`packages/connection/queries/dialects/oracle/query-compiler.ts`), never a per-query branch. App SQL targets 12c and up, so it never uses what a later release added (`NO AUTHENTICATION`, `VERSION_FULL`, `ALL_INDEXES.CONSTRAINT_INDEX`, `IF [NOT] EXISTS`, multi-row `VALUES`, a SQL `BOOLEAN`, `SELECT` without `FROM`); the Oracle schema typings leave such columns out. A name the app suggests (a constraint, an index, the default `id` column) folds to the engine's case through `suggestedName`, and a name the user types into a create or rename form through `submittedName`, which leaves a name the user did not change alone. So Oracle never stores a lower-case name every later reference must quote. A `LONG` column (`ALL_VIEWS.TEXT`, `ALL_TAB_COLS.DATA_DEFAULT`, `ALL_TRIGGERS.TRIGGER_BODY`) goes through no SQL function, `CASE` or comparison: it is selected bare and trimmed in the query's `.pipe()`, and a `_VC` twin is preferred where one exists. Oracle stores `''` as `NULL`.
- **An Oracle connection's resource is the service name in its string**, never one read back from the server, which spells it its own way (`freepdb1` for `FREEPDB1`) and would add a second resource; its schemas are the users it can see, and the default schema is the login's own, upper-cased (`describeConnectionString().defaultSchema`). Oracle commits DDL implicitly like MySQL, so `ddlRollback` is false. A read-only Oracle transaction (MCP's `query`) fails with ORA-01466 on a table whose DDL is newer than its snapshot, for a few seconds after the change; that is the accepted edge of keeping read-only enforced by the server.
- **SQL Server takes some object names as a string, not as identifiers** (`sp_rename`'s `@objname`, `OBJECT_ID()`), so `sql.id` never reaches them: every part goes through `mssqlQualified`, which brackets each part and doubles a `]`. A name holding a dot otherwise parses as a qualifier.

## Cancelling a running query

Aborting the request never stops the database: Postgres, MySQL and ClickHouse keep executing a statement whose client went away. So every `QueryExecutor` takes an optional `queryId` on `execute`/`executeTransaction` (the client sends Kysely's own compiled-query id) and exposes `cancel`, which each engine implements natively — `pg_cancel_backend` and MySQL's `KILL QUERY` over a **separate** connection (the pools hold one, and it is busy), `request.cancel()` on SQL Server, `KILL QUERY` by `query_id` on ClickHouse, and node-oracledb's `connection.break()` on Oracle, which interrupts the busy connection itself. SQLite is the exception: `node:sqlite` runs a statement synchronously, so it has finished before a cancel can arrive, and a Turso or D1 request cannot be called back, so its `cancel` does nothing. The registry is keyed by connection string as well as id, so cancelling needs access to the connection, not just a guessed id. A new transport (proxy, IPC, CLI) has to forward `cancel` like the other seven methods.

## Runner results and transactions

- **Every executor answers with `ResultSet[]`**: columns in order with duplicate names kept, rows as arrays, the affected-row count for a write, and `truncated` once rows pass the optional `maxRows` (`RunOptions`). Each executor reads rows through its driver's event stream and keeps at most `maxRows + 1` per set, so the cap bounds memory; only ClickHouse (`max_result_rows`), SQLite and Oracle also stop reading the rest (a SQLite `RETURNING` write has made all its changes by its first row; an Oracle write returns no cursor, so closing one only ends a query). The others read to the end: stopping them means cancelling, which aborts the statement, so a `DELETE … RETURNING` past the cap would roll back along with the rest of its batch. A statement with several sets (a SQL Server batch, a MySQL `CALL`, a Postgres text of several statements) answers with one set each; the SQLite and Oracle drivers run only one statement per call, so their executors split a text without bound values with `@tamery/sql`'s `splitStatements` first; for Oracle (`DialectSpec.plsqlUnits`) a `DECLARE`/`BEGIN` block or a `CREATE` function, procedure, package, trigger or type keeps its own semicolons and runs to a `/` line or the end of the text, as SQL*Plus reads it. Only the runner (`DialectOptions.resultSets`) keeps the sets; the app's Kysely driver and the CLI read the first set as row objects through `rowObjects`.
- **The SQLite executor runs each kind of SQLite connection through a transport** (`domain.md` → Connection): `node:sqlite` for a file, Cloudflare's REST `raw` endpoint for D1, `@libsql/client/http` for libSQL. A transport supplies only how it runs statements and holds a transaction (`SqliteTransport`, `queries/dialects/sqlite/run.ts`); value conversion, result sets, read-only checks and sessions are shared, so a bound value is stored the same way in all three. A file opens per call, and a transaction or session on a handle of its own, so the app's queries never land inside a transaction or keep reading a file another tool replaced, and a runner temp table or `PRAGMA` lasts one run unless a session holds it. Neither remote transport holds a connection between requests: `openSession` refuses with a pointer to **Run all**, a whole `BEGIN … COMMIT` script runs as the transport's own transaction, and a lone `BEGIN` or `COMMIT` in a script is refused before anything runs. Turso and D1 let a read-only transaction write, so every transport refuses a statement `readsOnly` rejects. D1 has no interactive transactions at all: a write transaction collects its statements and sends them as one batch on commit, which D1 runs atomically, so a statement inside one answers with no rows.
- **ClickHouse SQL runs on 21.12 and up**, with no version check: deletes go out as `ALTER TABLE … DELETE` mutations like updates (`prepareQuery`), a new row lists only the columns it sets (no `DEFAULT` in VALUES), a Map or Tuple value falls back from `format()` to `JSONExtract`, a Map through its key-value pairs (`clickhouseWrite`), a catalog column a newer server added is read with a fallback, an output setting the server calls unknown is dropped for that connection, and an error that stops a started stream, which an older server appends as a plain-text row, is parsed from that row (`run.ts`). A new statement or setting has to exist in 21.12 or get the same kind of fallback.
- **ClickHouse has no transactions**: its executor's commit and rollback are no-ops (a `read only` access mode still holds, as the `readonly=2` setting on every statement), so `DialectSpec.transactions` is `false` and the parser never groups a `BEGIN … COMMIT` there. `statementQuery` (MCP's `execute`) refuses text that opens a transaction without closing it (`leavesTransactionOpen`) on every engine: the pools hold one connection, so a transaction left open would carry every later app query.
- **A runner tab's transaction left open runs on a session** (`openSession`): a connection of its own, outside the pool, registered like a transaction so the idle timeout and `ownerId` apply. The executor opens nothing on it; the tab's SQL runs there verbatim, and after each run the tab asks `transactionStatus`, which reads the engine's own state (Postgres's ready-for-query status, MySQL's in-transaction status flag, SQL Server's `@@TRANCOUNT` and `XACT_STATE()`, SQLite's `isTransaction` on the session's own handle, node-oracledb's `transactionInProgress` on Oracle) as `open`, `failed` (only a rollback works: Postgres after any error, SQL Server's uncommittable state, so the tab offers no Commit) or `ended`, and releases a session whose transaction ended, since parsing cannot tell a SQL Server savepoint rollback, a nested `COMMIT` or MySQL's implicit commit from an ending. Any opener syntax and an SSMS-style `BEGIN TRAN` batch work unparsed, and the app's own queries never see the uncommitted rows; the runner skips its post-run refresh while the transaction is open, since the pool would wait on its locks. A database that refuses the second connection gets an error pointing at running the whole block in one go, which stays on the pool. SQL Server's session sends its SQL as a plain batch (`sp_executesql` rejects a batch that changes `@@TRANCOUNT` and drops its `#temp` tables), while the pool keeps `sp_executesql` so error 266 still refuses a transaction left open there. Its session pool keeps `min: 1`, or the idle reaper would close the connection and the transaction with it.
- **A transaction opener's isolation level and access mode travel as Kysely's `TransactionSettings`** into each executor's `beginTransaction`, which spells its own opener (SQL Server's `BEGIN TRAN` carries neither; MySQL's `START TRANSACTION` carries only the access mode, so the isolation level goes in a `SET TRANSACTION` right before it; SQLite is always serializable and spells read only as `PRAGMA query_only`; Oracle opens its transaction at the first change, and its `SET TRANSACTION` takes `READ ONLY` or an isolation level, never both). An executor that ignores them silently turns `BEGIN READ ONLY` into a writable transaction.
- **A multi-user transport passes the caller as `ownerId`** on every transaction call (`createQueryRouter`'s `owner` resolver); a `txId` alone must never drive another user's transaction.
